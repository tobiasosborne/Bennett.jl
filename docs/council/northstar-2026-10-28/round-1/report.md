## Blocking issues

- **[codex] B1_EFFECT_DOMAINS** (§§0, 1.3–1.4, 3 effects row, 5, 7): The unrestricted controlled-anything promise conflates classical reversibility with quantum coherence. Recording a measurement result does not restore the discarded coherence, and recording external output does not make the external observer reversible. A bounded deterministic simulation of SQLite or Linux can become a coherent oracle; an execution that exposes branch-dependent information to an ordinary console, filesystem, or measurement record cannot generally be uncomputed into that oracle. Likewise, replaying one recorded environment is not equivalent to evaluating every superposed input against a live environment. [Measurement and reversibility](https://arxiv.org/abs/1808.08598). *Fix:* Define separate execution capabilities for classical execution/replay, coherent reversible computation, and measurement-bearing computation. Preserve broad language coverage through an explicitly modeled environment: specify inputs, randomness, memory, bounds, and effects included in the reversible state. Require external effects to be coherently modeled or deferred where coherent control is promised; define rejection or another explicit semantic outcome otherwise. State the defined LLVM execution domain, including the treatment of undefined behavior.
- **[codex] B2_LLVM_CONTRACT** (§3 and §8.1): The extension-point table asserts guarantees these mechanisms do not provide. Target extension types are not linear; address spaces qualify pointers rather than arbitrary iN values; unfamiliar instruction metadata can be dropped; and llvm.lifetime.end describes memory lifetime, not quantum cleanup. [LLVM language reference](https://llvm.org/docs/LangRef.html). Convergence constrains particular control-flow transformations rather than furnishing general quantum effect semantics. [Convergence semantics](https://llvm.org/docs/ConvergentOperations.html). Genuine new llvm.* intrinsics require LLVM-side definitions, unlike Enzyme-style external marker calls. [Extending LLVM](https://llvm.org/docs/ExtendingLLVM.html). Consequently, the claimed blanket legality does not follow from the proposed mechanisms. *Fix:* Commit to a viable conservative no-fork representation: distinguish classical computations awaiting coherent lifting from explicit quantum state and effects; use ordinary effectful marker calls where necessary; carry mandatory bounds and lifecycle operations semantically rather than solely as metadata. State where verification and quantum lowering occur relative to ordinary optimization. Exact attributes may remain a design question, but their claimed guarantees cannot remain settled facts.
- **[codex] B3_COHERENT_RUNTIME** (§§1.6, 3, 4, 8.3–8.7): A classical runtime cannot inspect a superposed trip count, allocation decision, pointer, or garbage value to choose an ordinary execution path without potentially destroying coherence. Nor can classical checkpointing be transferred to arbitrary quantum states by copying them. Maximum-bound padding addresses execution length, but does not specify coherent allocation, history, release, or what happens when only some branches exceed a bound. Leaving these as unrestricted resource policy risks building a reversible classical debugger and calling it a quantum VM. *Fix:* Require scheduling decisions either to depend only on classical information or to be implemented coherently. Identify coherent versus classical heap, history, and control state; define bound-exhaustion semantics and the memory/recursion bounds needed for specialization. Specify clean release and dirty borrowing as semantic obligations, including restoration of correlations with external reference systems. Defer the scheduling algorithms, not these invariants.
- **[codex] B4_QUANTUM_CORRECTNESS** (§§2, 5, 7, 8.8): Matching native bit outputs and returning ancillae to zero does not establish a correct quantum oracle. A circuit implementing |x,0> → (-1)^g(x)|x,f(x)> passes those checks while introducing an unintended phase; even a global phase becomes observable when the operation is controlled. Measurement-bearing programs require comparison of quantum instruments or channels, not merely recorded outcomes. The current success definition can therefore certify artifacts that break the flagship quantum algorithms. *Fix:* State the intended phase-sensitive oracle embedding and the semantics of general quantum operations, including entangled inputs and dirty ancillae. Add small exhaustive operator/channel checks and interference tests to the ladder. Specify approximation budgets for rotations and hardware lowering, and identify what proof-carrying output proves, under which assumptions, with what independent checking. Describe differential testing as evidence rather than universal proof.
- **[muse] B1** (§3): Several rows are false as stated: llvm.lifetime.start/end annotate memory objects, not SSA garbage values; LLVM loop metadata is droppable and cannot carry load-bearing bound semantics; target extension types do not give linear ownership, because LLVM SSA uses may be duplicated, selected and threaded before any after-the-fact verifier runs; and a pass plugin cannot register new llvm.* intrinsics, only recognise calls to declarations. The iN-plus-taint row also conflicts with the target-extension-type row: ordinary iN values carry no address-space or per-value taint that survives optimisation. *Fix:* Rewrite the table around verified mechanisms: opaque declared marker functions rather than new intrinsics, bounds as explicit operands of marker calls, custom garbage markers, region outlining before general optimisation of tainted code, and a named pipeline placement. Make a legality spike against stock LLVM passes a gate on freezing bennett-dialect-spec.
- **[muse] B2** (§1.3-1.4, §6): 'Loaded by clang, rustc, and Julia without modification' and reuse of clang's GPU offload model are not true at the level needed. clang offload outlining, fat binaries and launch are front-end/driver mechanisms tied to language annotations and target triples, not something a middle-end plugin can conjure after taint analysis; rustc does not load clang pass plugins, does not use the clang driver, and exposes LLVM plugins only unstably; Julia integration is a separate problem the document itself defers in §8.9. *Fix:* Scope the claim: a clang/opt pass plugin first; rustc needs its unstable LLVM-plugin/codegen-backend path and Julia needs an LLVM.jl pipeline integration, each named as its own front-end integration. State that Bennett needs its own driver, link step and launch runtime (bennett-driver), with clang offload as the model, not a reused mechanism.
- **[muse] B3** (§4, §8.4): The ISA's central semantics are conflated: 'branch on a qubit' and 'loop while a quantum register is nonzero' cannot be classical instruction-pointer control in superposition; coherent control is predication padded to a maximum, as §4 half-admits, while measured feedback is ordinary classical branching. Until the vision says which class each ISA control instruction belongs to, 'one semantics, two executors' and 'circuit as bounded specialisation of the VM' are undefined, and the ISA spec, the VM and the specialiser would be built against different machines. *Fix:* Define two control classes in the vision itself: classical control flow on measured/host data, which is genuinely dynamic, and coherent control, which is predicated execution padded to a bound in both executors. State that the circuit is a specialisation of the VM only under that shared padded semantics, and drop any implication that run-time bounds unlock superposition trip counts.
- **[muse] B4** (§0, §3, §5, §7): An effect tape makes classical replay deterministic; it does not make I/O, syscalls, measurement or host filesystem access unitary. As written, Grover over SQLite executed 'by the actual SQLite engine' and amplitude amplification with 'the kernel panics' as oracle require coherent access to external state and an irreversible effect inside an oracle, which is physically incoherent. The same gap covers UB/poison, atomics, volatile, inline asm and exceptions: §0 promises universality for anything clang accepts, but no reversible semantics for undefined or effectful executions is stated, only deferred in §8.11. *Fix:* Add an effect boundary to the thesis: coherent regions are closed and effect-free, with classical inputs fixed before entry and outputs emitted after measurement; databases and kernels run as reversible code over reversible memory, with panic/query-match as computed predicates. Restate universality as covering every defined, effect-bounded execution, with trap/shim semantics for the rest, and rewrite rungs 4 and 7 accordingly.
- **[muse] B5** (§5, §7): Differential equivalence against native execution on classical inputs cannot detect relative-phase errors or residual garbage entanglement, yet the thesis is controlled-anything: an artefact correct on every basis state can be wrong under control and in superposition, which is the only place it will be used. 'It compiles and it is correct are the same statement' therefore overclaims, and 'proof-carrying circuit' is never given a checkable meaning. *Fix:* Redefine correct as basis-state differential equivalence plus phase-sensitive checks: unitary equivalence at exhaustive small widths and controlled/interference differential tests (run the artefact controlled and in interference against a reference), with proof-carrying output given a concrete certificate notion a checker can validate.
- **[muse] B6** (§1.6, §6, §6.1): The dialect spec and ISA spec are not sufficient for every pair of components to communicate, and §8.6 defers exactly the missing pieces: plugin, driver, runtimes and arith also couple through a reversible ABI, a linkable object format, a host/device launch ABI, and a cost-certificate format shared by circuits, arith, estimate and Bennett.jl. Two internal contradictions hide the monolith: §1.6 makes compiler and VM 'the same optimiser at two time scales' across the contract boundary, and §6 gives both executors 'one codebase' while §6.1 splits them into independently replaceable repositories. *Fix:* Either expand the ISA spec's stated contents to own the object/link format, reversible ABI, host launch/runtime ABI and cost-certificate schema, or name them as further contracts. Resolve the scheduler and one-codebase contradictions explicitly: what is shared, through which spec, such that a competitor's VM or specialiser could still replace either executor.
- **[opus] B1-dialect-extension-points** (§3 table, §1.2): Several extension points the dialect depends on are not available to an out-of-tree plugin, or do not do what is claimed. Out-of-tree code cannot add llvm.* intrinsics. Target extension type properties are hardcoded per name inside LLVM, so target("bennett.qubit") is unsized: it cannot be stored, alloca'd, made a global, or placed in memory aggregates, which rules out qubit arrays and 'quantum memory'. clang and rustc cannot emit the type from source. Address spaces and attributes cannot taint iN values. lifetime intrinsics apply only to allocas. Loop metadata is droppable and cannot carry a runtime bound operand. The cited examples (NVPTX, AMDGPU, SPIR-V) are in-tree. Built as written, the project would rest on mechanisms that do not exist. *Fix:* Restate §3 in terms of mechanisms that do exist: marker function declarations (Enzyme-style) with call-site attributes added by the plugin, handle retyping at PipelineStartEP, bounds as real operands of marker calls, garbage lifetime from liveness, and taint from analysis. Where a target-extension-type property entry is genuinely needed, say it will be proposed upstream (an upstream patch, not a fork), or design without it.
- **[opus] B2-qubit-semantics** (§3 rows 1 and 4, §1.7): The document wants qubits as 'SSA values … never opaque pointers' that are visible to dataflow, and also gates as intrinsics with memory effects so that passes cannot CSE, hoist or delete them. If gates have memory effects, the qubit is a handle whose state changes through hidden memory. That is QIR's problem again. Value semantics with readnone gates instead invites speculation that breaks linearity. Opacity does not prevent copies either, because SSA uses are free. This choice is the core design decision of the dialect, and CUDA-Q's Quake has both ref and wire forms precisely because of it. *Fix:* Decide value vs reference semantics, or say which form is used at which pipeline stage, at the vision level. State plainly that LLVM cannot enforce linearity, so linearity rests on a fail-loud verifier plus the legality contract.
- **[opus] B3-taint-compilation-model** (§1.3–1.4, §5 toolchain, §6.1 driver): Taint and controlled or adjoint bodies depend on the call context across the whole program. A function in one TU may be called under a qubit from another, and generating its controlled body needs its IR, which is Enzyme's own requirement. clang's offload machinery (outlining, fat binaries, launch) is driven by the frontend and driver over separately compiled device modules, so a pass cannot reuse it after the fact. As written, a per-TU plugin cannot decide what is 'never ours', and 'one reversible object per TU' is underspecified. *Fix:* Specify the compilation model. Every function is emitted natively and also carries embedded IR (a fat object). Device specialisation, taint resolution, and control and adjoint generation happen at link time (LTO plugin) or load time (runtime JIT). Define 'untainted' relative to the resolved call graph. The ISA lowering must accept host-triple IR (datalayout, ABI, target intrinsics, inline asm as trapped or shimmed).
- **[opus] B4-effects-under-superposition** (§3 effects row, §4 effect tape, §7 rungs 4/6–8): A recorded effect tape gives deterministic replay only for classical and reversible execution. In a superposed region, the effect sequence differs per branch, and a real outside-world effect (console, disk, a SQLite file read at a quantum-dependent address) decoheres or is simply undefined. The flagship rungs (Grover over SQLite, kernel fuzzing) depend on this semantics, which the document does not define. *Fix:* Define effect semantics per tier. The classical and reversible tiers may tape. The superposition tier must either trap on external effects or virtualise them as state inside the device (SQLite through an in-memory VFS over QROM/QRAM, devices modelled reversibly). Also state that VM run-time policy may depend only on classical data.
- **[opus] B5-repo-split-contradiction** (§6 Rust row vs §6.1, §1.6): §6 says the two executors live in one codebase, giving one semantics by construction, but §6.1 makes them independently replaceable repositories. Decision 6 says the compiler and VM are one optimiser, but the optimiser is split across C++ and Rust with no shared code, which breaks the document's own rule that C++ is used only where LLVM is linked. The host↔device launch ABI and the reversible object format belong to no contract. The split would be built wrong. *Fix:* Choose one executor arrangement and make the ISA spec's formal model plus the conformance suite the source of 'one semantics'. Move the scheduler and cost model into a non-LLVM component behind a specified interface used by both plugin and VM. Make the ISA spec explicitly own the launch ABI, object/linking format, and cost-certificate format.

## codex

The portable VM and resource-aware ISA are a strong direction, and the ambition is appropriate. Acceptance is blocked by four architectural semantic gaps: unrestricted control of effects, unsupported LLVM legality guarantees, unspecified coherence constraints on runtime scheduling, and a correctness definition that misses quantum errors. These require precise commitments in the vision, not completed implementations. The repository split, integration promises, resource claims, and prior-art positioning also need tightening.

- **C1 3**: The dialect, virtual ISA, resource scheduler, and demonstrations serve one ambitious objective. However, §§0–5 conflate reversible simulation of a closed computation with coherently controlling arbitrary programs that perform measurement or external effects. *Change:* State a precise coherent-lifting contract that distinguishes ordinary execution, recorded replay, and quantum-controlled execution.
- **C2 2**: The pass-plugin architecture and function-level transformation strategy are credible. Several guarantees attributed to LLVM extension points in §3 are false or unsupported: opacity does not enforce linearity, address spaces do not confer quantum semantics, and lifetime markers do not perform uncomputation. *Change:* Replace the extension-point table with a distinction between guarantees LLVM actually supplies and semantic obligations Bennett must enforce.
- **C3 3**: Virtual qubits, allocation classes, garbage occupancy, and classically supplied bounds form a compelling architecture; the maximum-bound padding statement is appropriately explicit. The missing distinction between classically inspectable scheduler state and coherent heap/history state leaves materially different machines consistent with §4. *Change:* Add an architectural invariant specifying which state scheduling decisions may inspect and how quantum-dependent allocation, termination, and history remain coherent.
- **C4 3**: The repository responsibilities are mostly sensible, but serialized program formats alone do not specify runtime invocation, results, diagnostics, or cost-certificate interchange. Section 6 also promises one codebase for both executors while §6.1 assigns them independent repositories; shared code would not establish semantic agreement anyway. *Change:* Inventory every component boundary and explicitly place its public interface under one of the two contracts.
- **C5 2**: Language-independent transformation of suitable LLVM IR without a fork is credible; unrestricted source and platform compatibility from one plugin flag is not established. Enzyme itself documents cross-translation-unit and LTO requirements, while rustc's plugin-loading interface has toolchain restrictions. [Enzyme integration](https://enzyme.mit.edu/getting_started/UsingEnzyme/), [rustc plugin interface](https://doc.rust-lang.org/nightly/unstable-book/compiler-flags/llvm-plugins.html). *Change:* Define the portable input and integration contract, including observable semantics, external dependencies, compiler-build compatibility, and coherent-execution eligibility.
- **C6 2**: Native differential testing is a substantial improvement over ancilla-zero checks, but it cannot establish the quantum correctness claimed in §5. The ladder lacks explicit phase, entanglement, dirty-ancilla, and measurement-channel criteria, and passing differential tests is not a proof that every accepted artifact is correct. *Change:* Make quantum semantic refinement, with explicit approximation allowances, the correctness criterion and retain native comparison as one supporting test.
- **C7 2**: The categorical account of an abstraction-free quantum ecosystem is false: OpenQASM 3 already provides dynamic control, and Tower provides coherent pointers, allocation, and classically bounded recursion. The document does not distinguish its proposed contribution from these or the other named predecessors. [OpenQASM 3](https://doi.org/10.1145/3505636), [Tower](https://arxiv.org/abs/2205.10255). *Change:* Add a concise prior-art comparison identifying the new combination and interoperability obligations, rather than claiming the existing abstractions are absent.
- **C8 3**: The document is readable, concrete about intended experiences, and appropriately separates vision from implementation. However, it labels architectural choices settled while deferring the semantic conditions needed to determine whether those choices describe a physically valid, optimizer-safe system. *Change:* Resolve the semantic commitments identified below at vision level, while continuing to defer their algorithms and encodings.

Suggestions:
1. Narrow the novelty claim to the proposed combination of ordinary LLVM program lifting, a portable resource-aware ISA, and coherent execution services. Compare explicitly with Silq's safe uncomputation, Q# and CUDA-Q control/adjoint facilities, Quipper's oracle construction, Catalyst's compilation pipeline, Tower's memory model, and reversible pebbling. [Silq](https://silq.ethz.ch/), [Q# functors](https://learn.microsoft.com/en-us/azure/quantum/user-guide/language/expressions/functorapplication), [CUDA-Q](https://nvidia.github.io/cuda-quantum/latest/using/examples/building_kernels.html), [Catalyst](https://docs.pennylane.ai/projects/catalyst/en/stable/index.html).
2. Correct the QIR critique: opaque pointers still participate in LLVM SSA dataflow, and emitted adjoint/controlled bodies do not prevent downstream analysis. The defensible criticism is missing explicit algebraic or ownership guarantees. Acknowledge existing adaptive profiles and allocation capabilities instead of implying that QIR lacks dynamic execution abstractions. [QIR memory management](https://github.com/qir-alliance/qir-spec/blob/main/specification/Memory_Management.md), [adaptive-profile capabilities](https://www.qir-alliance.org/posts/Adaptive_Profile_Helios_H2/).
3. Scope optimality certificates to a gate set, objective, accuracy, and search domain. Distinguish exact resource counts, certified bounds, and heuristic estimates; bounded execution does not itself guarantee cheap exact analysis. Specify resource units, composition rules, and optimization preferences. Qualtran's explicit symbolic counting contracts are relevant precedent. [Qualtran counting protocol](https://qualtran.readthedocs.io/en/latest/resource_counting/call_graph.html).
4. Give each marquee demonstration a reproducible bounded instance and explicit success assertions, including database loading, randomness/state preparation, environment modeling, and cleanup. This would make the ladder measurable without imposing an implementation schedule or requiring a claimed quantum speedup.
5. Complete the interface inventory with host/runtime invocation, quantum-handle ownership across calls, result and error schemas, certificates, and capability negotiation. Resolve the one-codebase versus independent-executors contradiction, and require agreement with the public semantics rather than agreement by construction.
6. Keep C++ as the pragmatic implementation choice, but correct the rationale: llvmGetPassPluginInfo has C linkage while its registration machinery uses C++ APIs; this does not prove that all implementation code must be C++. Also distinguish LLVM-major compatibility from exact toolchain ABI/build compatibility. [LLVM pass-plugin interface](https://llvm.org/docs/WritingAnLLVMNewPMPass.html).
7. Present maximum-bound padding as the specified coherent-loop execution strategy, rather than a universal optimality theorem imposed by physics. Variable-time amplitude amplification does not permit observing superposed stopping times, but demonstrates that worst-case padding is not the whole algorithmic cost story. [Ambainis](https://arxiv.org/abs/1010.4458).

## muse

The direction is right and the framing is strong: LLVM IR plus a C++ pass plugin on the Enzyme model, a versioned virtual ISA with garbage and resources in the architecture, two executors differentially tested against native execution, and a demo ladder that defines success. It is not yet founding-document precise, because several §3 extension-point claims are false as stated (lifetime intrinsics, semantic loop metadata, linearity from target extension types, plugin-registered intrinsics, rustc loading the plugin unmodified), the VM's coherent-control semantics conflate measured branching with padded predication, the effect/oracle story cannot support the SQLite and kernel demos as written, the correctness definition is blind to phase under control, and the two contracts omit the ABI/object/launch/certificate formats four repositories already couple through. All are corrigible without abandoning the vision, hence revise rather than reject.

- **C1 4**: §0's controlled-anything thesis, §1's decisions, §4's VM and §7's ladder do describe one artifact, and §4 is honest that superposition trip counts pad to a maximum. But the same document promises unqualified universality while its flagship demos (Grover over SQLite, kernel-panic oracle) need a closed, effect-free coherent world it never states. *Change:* State the effect boundary and the two classes of control flow (measured vs coherent) in §0/§4, so universality, the VM and the oracle demos describe the same machine.
- **C2 2**: The C++-only plugin argument in §6 (new-PM registration, SCEV/MemorySSA/CodeExtractor behind the C++ API, per-LLVM-version builds, Enzyme precedent) is correct. The §3 table is not: lifetime intrinsics do not annotate SSA values, loop metadata cannot carry semantics, target extension types confer no linearity against SSA duplication, and new intrinsics cannot be registered from a plugin. *Change:* Replace each row of the §3 table with the mechanism a stock-LLVM spike has actually verified, and demote the rest to §8 questions.
- **C3 3**: §4 articulates virtual qubits, allocation classes, garbage as a scheduled resource, the extensible resource vector and the effect tape, and states padded-to-maximum honestly. But 'branch on a qubit' as an instruction conflates measured classical control with coherent predication, so the execution model the ISA denotes, and hence the circuit-as-specialisation claim, is undefined. *Change:* Give the ISA two explicitly distinct control disciplines and one paragraph on what the VM physically is at run time: a classical runtime scheduling quantum operations, with coherent regions lowered to bounded predicated blocks.
- **C4 3**: §6.1's repo table and replaceability test are the right instinct, and the two spec repos owning nothing is clean. But reversible ABI/linking is deferred to §8.6 while four repos already couple through it, and §1.6/§6 contradict the split by sharing one scheduler and one executor codebase across the boundary. *Change:* Name every inter-repo format (object/link, reversible ABI, launch ABI, cost certificates) and assign each to a spec repo, or add the missing contracts.
- **C5 2**: §3 names real costs: a non-reversibility-aware optimiser, function-granularity regions, per-LLVM-version builds. It omits equally load-bearing ones: rustc cannot load the plugin as claimed, new address spaces need DataLayout/front-end cooperation, driver/link work is required for any host/device split, and UB/poison/atomics/inline-asm have no stated reversible semantics. *Change:* Add a per-front-end integration paragraph (clang plugin, rustc unstable plugin path, Julia pipeline) and a defined-semantics clause listing what traps instead of lowering.
- **C6 3**: §7's ladder is ordered and mostly measurable, §5's 'ancilla-zero is not correctness' and differential-against-native rule are exactly right for classical behaviour, and closed-form costs without materialised gates are coherent. But basis-state differential testing is blind to phase and garbage entanglement under control, and the quantum rungs state no scale or success metric. *Change:* Extend the definition of correct with phase-sensitive unitary and controlled-interference equivalence, and give rungs 4, 7 and 8 a size and an oracle construction.
- **C7 2**: The QIR critique in §1.7 (opaque qubit pointers, front-end-emitted adjoint/controlled bodies, no ownership, uncomputation or resource model) is accurate, and the Enzyme and PTX analogies are well chosen. There is otherwise no landscape engagement: Catalyst's MLIR-to-LLVM quantum JIT, CUDA-Q kernels, Silq's typed automatic uncomputation, Q#/Quipper/Tower, and Qualtran-style hierarchical resource estimation (which already does closed-form costs without gates) go unmentioned, so what is new is never isolated. *Change:* Add a short landscape section stating, per system, what Bennett takes, what it rejects and what is genuinely new: reversible semantics for arbitrary LLVM IR plus a virtual ISA with garbage in its resource model.
- **C8 3**: The document is unusually readable: §2's picture, §5's scenes and §8's deferred list let a compiler engineer see the shape at once. But a hardware vendor gets no example target description or ISA fragment, a language designer no minimal lowering example, and §8 defers items (legality contract, coherent-control semantics, reversible ABI) that are load-bearing for the vision rather than design detail. *Change:* Add one end-to-end worked example (a small function through dialect, ISA and cost certificate) and a minimal illustrative ISA fragment, so each of the three readers sees their surface concretely.

Suggestions:
1. Qualify §5's 'the compiler is optimal, and knows it': pebbling, scheduling and synthesis are hard in general, so claim optimality only within named policy/search classes with certificates, exactly as the small-exact/large-bounded sentence already half-does.
2. Give the resource vector a decision rule: if targets may add arbitrary resources, state how the scheduler scalarises or Pareto-ranks them, and what conformance can test about a resource the ISA does not enumerate.
3. Address adoption honestly: PTX and the JVM succeeded with a controlling vendor and a conformance regime; one paragraph on governance and why a hardware vendor implements this ISA before an ecosystem exists would strengthen §4.
4. Note the pipeline-placement consequence of 'optimise, reverse, optimise': unlike Enzyme's differentiation, reversibilisation is not invariant under information-erasing or UB-exploiting optimisation, so tainted regions likely need outlining and protection before the first optimisation, which is a front-end-visible cost worth stating in §3.
5. Rust ownership is affine, not linear (values can be leaked or forgotten); §6 should claim it models qubit ownership well with a leak check, not linearity natively.
6. Add an interoperation stance beyond edge formats: MLIR quantum dialects and Catalyst as an import path, and Qualtran/Azure-style target models as prior art for bennett-targets, so vendors with existing models have a migration story.

## opus

The north star is the right kind of ambitious. Treating the quantum VM and a public virtual ISA as the missing abstraction layer, staying inside LLVM rather than forking it, and defining correctness as differential agreement with native execution rather than ancilla-zero are strong, defensible choices, and §4's account of the pre-VM-era mistakes is the document's best writing. The central technical section (§3) overclaims what LLVM allows out of tree, and the gaps are load-bearing. Out-of-tree code cannot add intrinsics. Unknown target extension types are unsized and cannot be emitted by clang or rustc. Address spaces and attributes cannot taint integers. Lifetime markers and loop metadata cannot carry what the document needs. The NVPTX and SPIR-V examples are in-tree. The document also leaves undecided whether qubits have value or reference semantics, which is the very point on which it faults QIR. Taint is treated as a per-function property when it depends on call context across the whole program, so the compilation model (fat objects, link-time or JIT specialisation, host-triple IR) is missing. Effect taping is not distinguished from effects under superposition, and the flagship demos depend on that distinction. The repository split contradicts §6 on executors and on where the optimiser lives. Prior art (CUDA-Q, Q#, OpenQASM 3 modifiers, Quipper, Silq, Tower, Qualtran, SQUARE/Unqomp) goes unacknowledged, which blurs what is genuinely new. Fix the five blocking items and this becomes a credible founding document.

- **C1 3**: The thesis ('every program is already a quantum program', §0), the VM-as-revolution (§4) and the demo ladder (§7) do describe one thing. Two claims do not hold together, though. Decision 4 says untainted code is 'never ours', yet taint depends on the calling context: any function can be called under a qubit from another translation unit. And §5 says 'the compiler is optimal, and knows it', but optimal reversible pebbling is PSPACE-complete (Chan–Lauria–Nordström–Vinyals), so that claim is not coherent as written. *Change:* State that taint is a property of each call context across the whole program, not of each function. Then restate optimality as 'optimal within a declared search space, with certificates of the gap', not as absolute.
- **C2 2**: Several premises in the §3 table are false. Out-of-tree code cannot define LLVM intrinsics; Enzyme uses plain marker function declarations. LLVM hardcodes the properties of each target extension type by name (getTargetTypeInfo), so an out-of-tree target("bennett.qubit") has no layout and cannot be stored, alloca'd, made a global, or put in a memory aggregate. Unmodified clang and rustc cannot emit such a type from source at all. The cited examples (NVPTX/AMDGPU address spaces, SPIR-V types) are in-tree, not out-of-tree extensions. Address spaces and attributes cannot be attached to iN values. lifetime.start/end apply only to allocas, so they cannot mark SSA garbage. Loop metadata is droppable and is not a use, so it cannot carry a bound operand. 'Opaque, so no pass can invent a copy' is wrong: an SSA value can gain extra uses freely. rustc loads plugins only through the nightly-only -Z llvm-plugins flag. The C++-only claim and the optimise–transform–optimise transfer are correct. *Change:* Rewrite §3 so it lists only what an out-of-tree plugin can rely on: front ends emit __bennett_* marker declarations and opaque handles; the plugin retypes and attributes them at PipelineStartEP; bounds are real operands of marker calls; garbage lifetime comes from liveness analysis. Name an upstream LLVM patch (not a fork) wherever target-extension-type properties are actually needed.
- **C3 3**: §4's account of the pre-VM-era mistakes and the list of abstractions (virtual qubits, classes as register classes, bounds as values, garbage with an occupancy cost, a resource vector in the spec) are strong, and padding to the maximum trip count is stated honestly. Three things are missing. The effect tape only works for classical record/replay: an outside-world effect inside a superposed region cannot be taped, because its sequence differs per branch. A branch on a qubit pays for both arms, and a quantum-addressed load costs O(N) (QROM/QRAM); neither is said. And every run-time scheduling and pebbling decision may depend only on classical data, which is also unsaid. *Change:* Add an execution-semantics paragraph per tier. It should cover what effects may do under superposition (forbidden, virtualised inside the device, or decohering), state that run-time policy must be oblivious to quantum data, and give honest costs for branches on qubits and for quantum-addressed memory.
- **C4 3**: The replaceability test in §6.1 is the right test. But §6 says 'one codebase holds both executors, so one semantics by construction', while §6.1 puts bennett-vm and bennett-circuits in separate repositories. Decision 6 says the compiler and VM are 'the same optimiser at two time scales', yet the optimiser is split between C++ (plugin) and Rust (VM) with no shared code. The two contracts also leave out several real interfaces: the host↔device launch/runtime ABI, the reversible object/linking format, the cost-certificate format, and the Sturm gate record. bennett-arith and bennett-runtimes also have an undeclared build dependency on the plugin binary. *Change:* Resolve the executor contradiction. Move the scheduler and cost model out of the C++ plugin into a separately specified, non-LLVM component. Make the ISA spec explicitly own the launch ABI, object format and certificate format, or name them as additional contracts.
- **C5 2**: 'Any LLVM language, invisibly, with no fork' omits the real costs. Front ends cannot emit the dialect's types. rustc plugin loading is nightly-only, and the Rust Enzyme effort chose to integrate into rustc instead. Generating controlled or adjoint bodies on demand needs the callee's IR, as Enzyme does, which means LTO or embedded bitcode, not per-TU objects. clang's offload model is driven by the frontend and driver: a pass cannot reuse it after the fact. Device IR inherits the host triple's datalayout, ABI lowering, target intrinsics and inline asm, which matters for the kernel rungs. Without adding a clang target, which cannot be done by plugin, there is no 'bennett' triple. *Change:* Add a compilation-model section: fat objects that embed bitcode, device specialisation at link or load time (an LTO plugin or JIT), host-triple IR accepted by the ISA lowering, and inline asm and target intrinsics classified as trapped or shimmed. Add each of these to the list of costs.
- **C6 3**: Defining correctness as differential agreement with native execution, not as ancilla-zero, is right and well argued (§5). Rungs 1–3 are measurable. Rungs 4, 7 and 8, the ones that 'define success', have no criterion: is success simulator execution of a small instance, a resource estimate, or hardware? Differential testing against native also cannot check the parts that are not permutations (rotations, measurement, interference). 'Proof-carrying' never says what is proved. *Change:* Give each rung an acceptance test: instance size, which executor, which oracle (native for the permutation part, statevector simulation for the quantum part), and a resource-estimate deliverable. Then define what a proof-carrying certificate asserts.
- **C7 2**: Only QIR and OpenQASM 3 are discussed. CUDA-Q already treats quantum kernels as device code with a host/device split, generates control and adjoint at function granularity (cudaq::control/adjoint), and has to choose between value and reference qubit semantics in Quake. Q# generates Adj+Ctl specialisations from one body. OpenQASM 3 has ctrl@/inv@ modifiers. Quipper builds oracles from classical code. Silq, Unqomp, Reqomp and SQUARE do automatic or budgeted uncomputation. Tower has superposed pointers with bounded recursion. Qualtran gives symbolic costs without materialising gates. QSSA and QIRO cover linear SSA quantum IR. ReVerC does verified reversible compilation. None of these is cited, so what is genuinely new (unmodified C, Rust and Julia through inferred taint; a public ISA with a resource vector and run-time pebbling) is never separated from what is not. *Change:* Add a landscape section. It should say, per system, what Bennett adopts, interoperates with, or does differently, and claim novelty only for the inferred-taint, unmodified-language path and for the VM/ISA.
- **C8 3**: The document reads well and orders its open questions sensibly. A hardware vendor learns nothing concrete about the ISA: there are no instruction classes, no example, and no shape for a target description. Three load-bearing questions are missing from §8 or deferred as mere detail: value vs reference semantics for qubits, the separate-compilation and taint model, and effect semantics under superposition. The 'year of discussion with the field's leading figures' paragraph adds nothing. *Change:* Add a one-page sketch of the ISA with an example program and target description, and promote the three missing questions into §8 as the first items to design.
