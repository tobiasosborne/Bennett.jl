## Blocking issues

- **[codex] B1** (§§3.6–3.7, 4.2; T2; ?/?): The inverse remains incorrect for A+D rows. A forward lift.call changes sp and fp after pushing the record, but §3.6 tells the inverse to undo direct suboperations before restoring assignments. Consequently, its stack exchanges and metadata XORs use the new sp rather than the original record base. lift.ret similarly needs its original fp restored before reversing delivery and location exchanges. The text also gives no dependency-safe reversal rule for assignment destinations such as alloctab[old_atop]. The repaired pure-assignment example works, but T2 still fails for the stated mixed-row algorithm. *Fix:* Define inversion by reversing the complete ordered list of elementary suboperations, interleaving assignment restoration with direct inverses. For call, restore the counter assignments first, undo parameter binding and record construction at the restored record base, restore L_f, then uncompute captured arguments. For return, restore fp/depth before undoing delivery and location exchanges, then uncompute the captured result. Preserve every effective address until its last inverse use, either through retained address slots or an explicitly proved restoration order; I recommend literal reverse-order semantics with retained addresses wherever needed.
- **[codex] B2** (§§3.7, 16.2–16.3 Example 2; ?/?): Example 2 cannot satisfy its advertised success domain. If the named result r is a location, as its use as a recursive call destination and lift.ret operand requires, @sum has 3 parameters, 1 result location and 9 regs: R_f = 16 cells. Input n = 16 requires 17 activations and therefore 272 cells, exceeding the maximum stack_limit of 2^8 = 256. If the result declaration specifies only a width, r is undeclared instead. No permitted budget makes the stated n = 16 success case work. *Fix:* Explicitly define whether a named lproc result belongs to L_f and its declaration order; I recommend that it does. Increase Example 2's S_cells to 9 and recompute its affected hashes. Alternatively restrict its advertised success domain to n ≤ 15, but increasing the stack preserves the intended 16-byte example.
- **[codex] B3** (§§4.1, 7.4, 9.4, 10; T4; ?/?): Matching boundary argument/result values does not make a call segment reversible through intervening state changes. For example, f() reads pointer P and stores 1 through it. Start with P=A and A=B=0; call f, change P to B, then uncall f. The stored delta restores A. Re-executing f when reversing uncall now writes B, whereas the retained original call frames describe writes to A. Following those frames leaves B modified; replacing the segment with newly generated frames would be a different, unspecified history rule. Intervening allocations and device operations cause analogous interference. *Fix:* Permit segment uncall only when intervening frames are proven noninterfering with the segment's read dependencies, writes, allocator state, device state and quantum operands. Define the version checks, failure outcome and exact replay/history treatment; copying an immutable result can remain legal. Alternatively restrict uncall to an adjacent LIFO segment. I recommend the checked noninterfering form if compute-copy-uncall is required.
- **[codex] B4** (§§3.7, 4.2, 7.1–7.2; ?/?): Memory boundary semantics still have holes. Nothing explicitly rejects more pinned pre-entries than alloctab can hold. CC/R alloc has no stated heap-exhaustion or address-overflow check despite the declared maximum heap interval. Finally, inrange mandates ptr_width + 1 arithmetic even though its length operand can be wider; this conflicts with §3.7's widened-arithmetic rule and can truncate a large boundscheck length. *Fix:* Reject layouts whose pre-entry count exceeds table capacity. Define CC/R allocation failure before mutation when the prospective bump exceeds the heap interval or pointer range, with a CC trap and a specified R fault code. Evaluate every bounds comparison at a width sufficient for all address and length operands plus carry, and narrow only after successful validation.
- **[codex] B5** (§§3.1, 3.3, 4.7–4.8, 9.1, 16.2; ?/?): The claimed closed instruction and metadata schemas are still incomplete. §3.1 permits R functions to call Q regions, while §4.8 permits region calls only in Q and CC. Width and alias rules for label values, frame-slot padding and repeated assignment destinations are absent. qjumpr checks only a global numeric range without a complete rule preserving function/activation ownership. Action bounds remain an unexplained array, and the memoryless example omits layout although budget validation and construction otherwise require its fields. *Fix:* Publish per-opcode schemas and kind-specific metadata schemas with required fields, defaults and rejection rules. Specify hostcall request bytes, reply destination/capacity, rlen and failure atomicity, then map each completion/fault condition to launch states and allowed operations. Treat hardware cleanliness as a semantic or certified precondition, without promising a nondestructive test of an arbitrary quantum state.

- **[opus] B1** (§4.1 uncall, §7.4 segment uncall and whole-run reversal, T4; ?/?): Segment uncall reverses a call segment's frames while later frames stay in place, so recorded old-value restores are applied out of LIFO order. This is unsound on three counts. (a) Allocation: f does `alloc 10` (bump hb→hb+10, entry e0). The caller then allocates p2 = hb+10. `uncall f` restores the old bump pointer hb and the table entry. The next `alloc 20` returns [hb, hb+20), which overlaps the still-live p2. If the table is reset by index, p2's entry is lost as well. (b) Devices: console reversal 'pops' bytes the caller wrote after f; entropy `p -= len` rewinds behind later reads. (c) Whole-run reversal 're-executes reversed segments forward when it meets their uncall frame', and that execution starts from the state at that time, not the original one. Take entry C = 0. f reads B = 0 and writes A. The caller stores C = 7, then B = 5. `uncall f` follows. On reversal, re-executing f reads B = 5 and writes C = 1, recording old C = 7. The caller's frames are reversed (B←0, C←0), then the re-executed segment's frame restores C←7. The final C is 7, not the entry value 0, so T4 is false. Two executors would also disagree on where the re-executed frames sit in the history. *Fix:* Choose one of two semantics. (a) Recommended: `uncall @f (args)(results)` is legal only if every frame after the matched segment is pure: dynamic SSA instances, `br` frames, and loads that only create instances. Any store, alloc, free, effect, hostcall, qreg, measure, call or region-call frame after the segment makes uncall a CC trap / R fault FAULT_UB_TRAP. Executing uncall removes the segment by LIFO-restoring its frames and pushes an uncall frame holding the removed frames verbatim. Reversing that frame re-applies those frames' recorded new values in forward order (redo by delta, never re-execution). This keeps the compute–copy–uncall idiom and makes T4 follow from frame-by-frame LIFO. (b) Janus semantics: uncall runs @f's inverse on the current state. This needs an inverse-execution semantics for R functions and a precondition check that the post-state matches; it is much larger, and I would not take it now.
- **[opus] B2** (§3.7, §16.3 Example 2, §9.2 hash table; ?/?): Example 2 is a normative test vector, and its stated results are wrong or underdetermined. (i) No rule says whether an lproc's result name (`(r:reg[8])`) is a location, yet @sum writes `r = lift.call …`. If it is a location (required for the body to be well-formed), L_f has m′ = 3 params + r + 9 regs = 13, so R_f = 16. The 17 nested calls needed for n = 16 then require 17·16 = 272 > 2^S_cells = 256 stack cells, and since `stack_limit ≤ 2^S_cells`, n = 16 faults FAULT_BUDGET_DEPTH under every valid budget. The text claims success for n ≤ 16; that holds only if r is not a location (m′ = 12, 17·15 = 255), in which case the body is ill-formed. (ii) The final hash table still prints each hash equal to itself, the template error flagged as opus B5 last round. The @sum/@sum_db envelopes are not printed. I verified inc8 (d93adc99…) and `zero` (ff565436…) byte-for-byte, but could not reproduce @sum/@sum_db from the text alone. *Fix:* State in §3.7: 'an lproc's result name is a location of the lproc, numbered after its params and before its regs, and included in L_f'. Then either set S_cells = 9 in the layout (recomputing the hashes) or state the success range as n ≤ 15 with n = 16 → FAULT_BUDGET_DEPTH. The alternative is to drop result names (the signature carries a width only, and the body uses a reg); I prefer keeping the name as a location. Replace the hash table with `name = hash` rows and print the @sum and @sum_db envelopes as escaped listings, as was done for inc8.
- **[opus] B3** (§6.4, §8.3 mbu_schemes, §11 cleanup entries, §12.1 channel claims; ?/?): Measurement-based cleanup is the compiler's sanctioned strategy (north star §4.2, §5), but its realisation and its proof check are not pinned. (a) `mbu_schemes.template` is elided ('… measure/fixup steps …'). In any case the correct fixup is function-specific: after X-basis measurement of g's wires with outcome m, the phase (−1)^{m·g(x)} must be applied, and that needs g's computing sequence (or a phase oracle derived from it), which a target-level template cannot contain. Two executors honouring the same `realisation: mbu, mbu_scheme: s` binding would therefore emit different operation sets and costs, and verbatim schedule execution is undefined. (b) The `channel` claim checks 'SDP dual feasibility of (Y, mu) for the diamond-norm program' without stating which program, the Choi convention, or the ½ factor. One checker would accept a bound that another rejects. *Fix:* Make the MBU realisation normative in §6.4. For a cleanup of perm value g (width w) bound to its computing sequence S: apply `h` to each wire of g; measure each, giving m ∈ {0,1}^w, recorded classically; release the wires; then, if m ≠ 0, apply the fixup. The fixup is to recompute g into a fresh clean bundle via S, apply `z` to bit i for each m_i = 1 (classically conditioned), and uncompute via S⁻¹. The fixup's ops are expanded with ordinals like any generated operation. A target's mbu_scheme then supplies only costs and feedforward latency, and may name an alternative fixup only as a separately certified scheme. For channel claims, state the program: with unnormalised Choi J(Φ) = Σ_ij |i⟩⟨j| ⊗ Φ(|i⟩⟨j|) and Φ = Φ_real − Φ_ref, accept the bound iff Y ⪰ 0, Y − J(Φ) ⪰ 0 (verified by interval Cholesky or a Gershgorin/eigenvalue enclosure at precision_bits), λ_max(Tr_out Y) ≤ mu, and 2·mu ≤ bound (Watrous's simplified SDP, ‖Φ‖◇ ≤ 2·mu).
