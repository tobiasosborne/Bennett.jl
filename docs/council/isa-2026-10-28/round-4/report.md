## Blocking issues

- **[codex] B1** (§§3.6, 4.2, 5.2; T2): The stated inverse is not the inverse of the forward step. After undoing the pc exchanges, it never undoes the successor XOR into pc'; after exchanging displaced values back, it never uncomputes the computed values remaining in disp_j. A lift.const 5 step with successor 1 therefore leaves pc'=1 and disp=5 after the listed inverse. Moreover, 'the same controlled operations' is false for a general lift.perm_call: a permutation need not be an involution, and composite direct operations require reversed order. *Fix:* Specify the inverse in exact reverse dependency order: reconstruct dispatch, undo both pc exchanges, undo successor accumulation while flag/succ are available, invert each row's direct suboperations in reverse order, restore assignment destinations, uncompute every assignment value from the restored old state, clear succ/flag, and clear dispatch from the restored pc. A permutation call must invoke its actual inverse. Define the interleaving for A+D rows explicitly, including retained effective addresses.
- **[codex] B2** (§§3.6–3.7, 4.2, 16.3): The return protocol is inconsistent. Both examples declare result r and execute lift.retval r, whose row performs result ^= v: this is r ^= r, yielding zero classically and lacking the claimed direct-permutation implementation. lift.ret uses record.v although the record has no such field or defined operand-to-slot mapping. Recursive calls move the callee's locations before copying arguments that may occupy those locations, without specifying how their old values remain readable. Example 2 additionally gives separately linkable lprocs implicit access to enclosing-oracle locations and global loads. Finally, label indices are ordinary reg values, so observable numeric indices conflict with unrestricted re-indexing. *Fix:* Use a dedicated return accumulator, distinct from every permitted return source, or make lift.retval only select the return value without modifying it; I recommend the dedicated accumulator. Define the complete ordered location set, old-argument capture, return-value capture and destination update for call/ret. Choose assignment or XOR semantics for call results explicitly. Require explicit capture parameters and explicit global load rows, or specify and hash an equivalent lexical environment; I recommend explicit parameters and loads. Make labels opaque, or preserve their canonical observable numeric representation during re-indexing.
- **[codex] B3** (§§3.3, 3.5, 4.6, 5.3, 6.4): Operand disjointness does not include implicit predicate controls. Consequently qpred p; x p; qunpred p is not explicitly rejected, although controlling X on its own target maps both basis values to zero. qif and its adjoint also require the branch selector to remain stable. Measurement-based cleanup eligibility checks inherited invocation controls, but does not clearly account for predicates introduced locally around the cleanup. *Fix:* Require every active or inherited control to be disjoint from every target and consumed allocation, and require predicate selectors to remain unchanged until their matching pop. Define duplicate-control handling and its accounting. Apply the unitary-cleanup restriction to the complete effective control context at each cleanup site, including local predicates; alternatively admit controlled measurement-assisted cleanup only through a separately specified controlled-channel contract.
- **[codex] B4** (§5.6; §12.1 toggling_lemma): The replacement toggling lemma is false for the permitted permutation gates. Let V = cx x b and W = swap y z; cx b y, with b borrowed and X={x}. All four written conditions hold, including target/control disjointness. For x=y=z=0, V;W;V⁻¹;W returns b unchanged but produces y=z=b. Public outputs therefore depend on the borrowed value. Affine dependence on b alone does not imply that the repeated W cancels it; standard toggle detection also needs an appropriate self-inverse operation. [Khattar–Gidney, §4](https://arxiv.org/html/2407.17966v2) *Fix:* Restrict the structural rule to an explicit translation form: V maps b to b XOR f(X), and W maps Y to Y XOR g(b,Z), with X, Z and all controls unchanged, Y disjoint from controls and borrowed wires, and g affine in b. A sufficient syntactic rule uses only X-family target flips with globally disjoint control and target sets; arbitrary swaps are excluded. Alternatively remove this structural rule and require a full T3 claim. I recommend the restricted translation lemma.
- **[codex] B5** (§§3.7, 4.2, 7.1–7.2, 10, 16.3): Memory initialisation and validity are still incomplete. Pre-entered pinned allocations require atop to start at their count, but this initial counter value is not stated. Heap limits are checked against physical capacity without explicitly enforcing heap_limit_max and disjointness from mapped interface ranges. Example 2 permits a heap extending from 32 to 8192 while db occupies 4096–4111. The separate boundscheck instruction is not explicitly tied to the same address version and byte length as the subsequent access. Counter-width comparisons also need widening when an allocation size or prospective sum exceeds that width. *Fix:* Define the complete initial allocator state, including atop, bump pointer, counters, table order and zero-filled storage. Validate a disjoint maximum heap interval at load time and require each token's heap limit to fit it. Either make every load/store perform its own bounds check or require a verified matching check over the identical address version and full access length; I recommend checks in the reference access semantics. Perform prospective arithmetic at sufficient width before narrowing. Correct Example 2's heap interval.
- **[codex] B6** (§§3.3, 4, 9.1, 16.1–16.2): The claimed complete operand and metadata schemas are still sketches. A CC const or zext has no encoded result type or complete inference rule; ptrtoint/inttoptr width semantics are absent. Tier applicability, register-id-to-wire binding and caller-owned region binding are not defined sufficiently to express device CC register management independently. Metadata fields lack complete types and required/optional rules: for example, the lproc signature in Example 2 omits fields presented as mandatory by <sig>. Modifier syntax and several instruction forms remain delegated to schematic prose. *Fix:* Publish a closed per-opcode schema covering tier, operands, result types, literals, widths, aliases and modifiers, plus concrete schemas for every metadata section. Add explicit result type annotations where inference is not unique. Define the CC representation and operations for quantum-register handles and region arguments. Specify kind-dependent signature fields, canonical ordering, numeric encodings and rejection rules, then make every example conform.
- **[codex] B7** (§§7.1, 7.3–7.4, 10; T4): The retained history cannot yet restore all declared state. entropy.read and block.read overwrite classical memory, but an effect frame retains only a tape index and the tape records args/results, not the overwritten destination bytes. Rewinding the entropy position does not restore those bytes. Block writes must distinguish an absent sector from a present zero sector. Allocation reversal does not explicitly restore the bump pointer and initialised storage. The clock operation also contradicts the blanket statement that device results are written through memory arguments, and the history treatment of uncall itself is unspecified. *Fix:* Give every effect an exact typed signature and reversible delta, including overwritten memory, device counters, sector contents and sector-presence bits. Record allocator cursor and storage changes. Define whether uncall removes an adjacent call trace or records an inverse operation that can itself be reversed. State failure atomicity and restoration rules for faulted effect prefixes. These rules should make T4 follow directly from the frame table.
- **[codex] B8** (§8): The target language remains underdetermined. General log2inv_eps values are irrational, so they cannot be evaluated in the promised exact-rational arithmetic; eps=0 is left undefined when an entry declares epsilon=0. AST arities, variable availability and table range errors are missing. Schemes have no opcode applicability, operand-class/control signature or complete wire/parameter binding, and their repeat variable cannot be referenced by the closed expression grammar. Resource kinds also lack complete rules for custom occupancy rates and concurrent peak demands. *Fix:* Define every AST operator and its domain. Prefer an integer ceil_log2_inv_eps primitive with exact comparison semantics, and prohibit logarithm evaluation in exact mode; rigorous interval evaluation is a viable alternative. Give schemes explicit applicability signatures, input/control/target/scratch bindings, scoped variables, expansion rules and dependencies on native entries. Define aggregation from scheduled events and live intervals for every resource kind, including concurrent demands, rates and objective validation.
- **[codex] B9** (§§9.2–9.3, 12.3, 16.3): The semantic envelope still does not have one complete interpretation. 'Reached' layout entries are not a sufficient dependency rule: an otherwise unread global changes the number of pinned entries and can change allocation faults. Section 9.2 specifies JCS entry lines, while Example 2 introduces dotted-name-prefixed lines. SCC substitution does not explicitly resolve the separate referenced-hash list for intra-SCC dependencies. Hashing only ISA MAJOR also needs a compatibility rule that explains semantic changes between these 0.x drafts. Executable certificate closure_hash remains optional. *Fix:* Hash all semantic initialisation inputs, including every pre-entered allocation and relevant device model, or define a conservative dependency closure that necessarily includes them. Specify one byte-level envelope format and apply SCC placeholders to every dependency occurrence, including the dependency list. Bind the precise semantic version and require resolved closure identities for executable certificates and caches. I recommend a tagged canonical envelope with reference vectors for acyclic and recursive examples. The inc8 hash itself reproduces correctly under the stated trailing-LF envelope rule.
- **[codex] B10** (§§9.4, 10–11): The C API now has builders, but its behavioural contract remains incomplete. There is no normative mapping from argument-array entries to CC wire/region parameters, no lifetime rule for asynchronously used args and entropy buffers, and no complete rules for tokens, borrowed accessor buffers or unload with live runs. qreg_prepare does not state whether it requires a clean register or performs a reset channel. Close, ownership release and returned register validity are not fully specified. The scheduling opaque types are also used without declarations. *Fix:* Define positional typed argument and region bindings, byte encodings and widths, ownership/copying at each call, buffer lifetimes, token scope and destruction, and every run/qreg transition with its status result. Choose clean-only basis preparation or explicit reset semantics; I recommend clean-only preparation plus a separately named reset operation if needed. Specify close/unload effects on all handles and add the missing opaque declarations. Publish this as one self-contained versioned header and behavioural contract.
- **[codex] B11** (§§9.4, 11–12): The hierarchical schedule still cannot be executed verbatim by independent executors. One iteration field does not identify nested loop iterations or repeated calls at multiple levels. Generated categories such as comparator identify many operations without defining their expansion or individual identities. Overlapping selectors have no complete specificity/tie rule. A cleanup marked mbu carries neither a particular measurement/fixup realisation nor a binding to one, and class any still leaves an allocation decision to the consumer. Different legal executor lowerings therefore need not share the scheduled operation set. *Fix:* Bind schedules to a normative hierarchical realised-operation graph, either carried in the schedule or expanded from versioned templates. Give each nesting level its own occurrence/iteration and phase coordinates, define deterministic selector resolution or reject overlaps, and bind every decomposition, cleanup instrument/fixup and allocation class. Validate dependency order, control context, timing, accuracy and capacity on that graph. I recommend carrying the hierarchical graph so executor optimisations cannot silently reinterpret schedule entries.
- **[codex] B12** (§12; T6; suites C–D): Certificates still lack executable proof rules. An intervals array has no defined relationship to matrices, channel constructions or a norm-bound derivation; inverse_pair_library and adjoint_table witnesses are unspecified. A single 64-bit PRNG output cannot sample a component whose range exceeds 2^64, although wider bundles are allowed. The all-zero xoshiro state is also not rejected, contrary to the generator's requirement. Minimality claims promised by the north star have no witness format. Finally, T6 states an operator-norm conclusion for actions without requiring that their inclusive bounds actually use that metric. [xoshiro256** reference implementation](https://prng.di.unimi.it/xoshiro256starstar.c) *Fix:* Define complete claim schemas and versioned checking algorithms, including realised-artifact identity, structural rule payloads and rigorous matrix/channel bound witnesses. Assemble enough PRNG words for each component, specify word order, rejection and offset rules, and reject the zero seed. Add checkable lower-bound/exhaustive-search witness formats for supported minimality claims, or explicitly prohibit such claims in this version. Preserve metric types through composition: operator conclusions require operator bounds, with the stated conversion only toward channel bounds.
- **[muse] B1_RETVAL_RET_DELIVERY** (§3.7, §4.2 lift.ret/lift.retval, §5.2 commit, §14.1, §16.3 examples): `lift.retval` is defined as `result ^= v`, commit XORs `result` into tgt, and both examples declare `result r` naming the location that already holds the answer and emit `lift.retval r`. If `result` is that location, the row computes r ^= r = 0 and inc8 returns 0, contradicting its own text; if `result` is a distinct internal register, the `result r` declaration and §3.7's `result: reg[T]` are meaningless and §14.1 never says the payload is v. Two executors will pick differently. The same defect recurs in `lift.ret`: it XORs `record.v` into the destination although the record layout in §3.7 has no v field, no rule says which record cell holds the operand after the L_f exchange, and XOR is not assignment — for a destination location holding a nonzero old value (any second call in a loop) the step construction yields old XOR v where the reference interpreter, which alone defines F_B, assigns v. Construction and reference therefore compute different functions. *Fix:* Pick one payload semantics and state it once. I recommend: delete `result` as a named location from oracle/lproc declarations; introduce a distinct internal step-state register `result_val`, initially 0, whose width is the signature `tgt` width; define `lift.retval v` as `result_val ^= v` (v any readable location/pseudo-location) and commit from `result_val`. For `lift.ret`, deliver by exchange, not XOR: copy the operand value into a dedicated frame disp slot before exchanging L_f back, then swap that slot with the unique location whose id equals record.dest (the slot retains dest's old value); state the inverse in that order and count the slot in k_max. Also state the declaration order that defines L_f and location ids (params, then regs, in text order, per function in index-space order). The alternative — payload is the named result location, `lift.retval` writes nothing and its operand MUST be that location, and call destinations MUST be provably clean — also works but forces producers to zero destinations before every call in loops, so take the exchange version.
- **[muse] B2_EXAMPLE_NAME_RESOLUTION** (§3.7 pseudo-locations, §4.2 read operands, §16.3 Example 2 and its commentary): Example 2 is not well-formed under §§3.7/4.2 and its commentary invents two semantic rules found nowhere else: `zero` used as a read operand 'denotes a lifted load of its image width at its base' with a boundscheck the dialect 'emits' (but the object holds only the reference body, so those rows, and their budget steps, either exist or do not), and @sum reads `base`, a mutable location of the enclosing oracle, justified only by the sentence 'lprocs read the enclosing oracle's locations as pseudo-locations'. 'Enclosing oracle' is undefined for an lproc linked into several oracles or called from another lproc, nothing says whether the read sees the value at oracle entry or the current value, and §3.7 defines pseudo-locations as interface inputs only, never writable — oracle locations are writable. A producer and an executor will disagree on whether this body is legal, what it reads, and how many steps it takes. *Fix:* Remove both invented readings rather than normativising them, since C semantics is pointer-based (the same reason the editor declined region-named loads). Rewrite @sum: take the database base as an explicit third parameter threaded through the recursive calls (or materialise it with lift.const in each activation), and read the global the ordinary way — a pointer constant for its layout base, lift.boundscheck, lift.load.i8 — or compare against a lift.const 0 location if no global read is needed. State the closed name-resolution rule in §3.7: a read operand in a lifted row is exactly a location of the containing function or an interface pseudo-location (in/args) of the containing oracle; lproc bodies see only their own locations plus the oracle's in/args pseudo-locations, never its mutable locations; a global's name is not an operand. Recompute the example hashes under the rewritten body.
- **[muse] B3_UNCHECKED_LIFTED_ACCESS** (§4.2 lift.load/lift.store/lift.boundscheck, §7.2, §14.1, T1): Nothing requires a lift.boundscheck before lift.load/lift.store in a well-formed body (§5.1 lists no such rule; it is only a property of bodies the dialect mapping produces). For a syntactically well-formed oracle that loads at an input-derived address >= 2^H or outside every allocation, the reference interpreter (§14.1, cells 'are arrays') has no defined value, while the §7.2 construction uses 'the low H bits' and wraps into a live cell — two different functions, and T1's claim that F_B is defined for every well-formed oracle is false. A hand-written or competitor-produced object, which the spec exists to admit, hits this immediately. *Fix:* Give lift.load/lift.store the same flag as lift.boundscheck for their own address and length: flag = (p >= 2^H) or not-exists live entry containing [p, p+N/8), computed without wrap at max(ptr_width, Hc) bits; C = FAULT_UB_MEMFAULT; successor HALT on flag; the access (assignment) executes only under not-flag. Keep lift.boundscheck as an explicit assertion row for compatibility — after a dialect-emitted boundscheck the load's own flag is never set, so reference step counts and F_B for dialect-produced bodies are unchanged — and state in §14.1 that the reference interpreter applies the identical check. The alternative, a suite-F rule requiring a dominating boundscheck with identical (p, n) operands before every access, also restores totality but makes legality depend on a dataflow check two verifiers must implement identically; take the inherent check.
- **[muse] B4_TOGGLING_LEMMA_DISJOINTNESS** (§5.6 toggling lemma, §12.1 structural claims): The toggling lemma as stated is unsound. It never requires X to be disjoint from the borrowed set, never states that V's controls lie in X and its targets only in the borrowed set, and condition (ii)'s 'outside W's own controls' does not say whether target/control disjointness is per-gate or over all of W. Counterexample satisfying all four printed conditions with borrowed {b1, b2}: V = cx b2 b1 (XORs into a borrowed wire a function of X = {b2}); W = cx b1 t (writes no wire of X, target outside X/borrowed/controls, one borrowed control); frame V;W;V^-1;W leaves t ^= (b1 XOR b2) XOR b1 = b2. The public output depends on a borrowed value and entangles with it, yet a structural certificate claim of kind toggling_lemma would label this proof — exactly the failure mode opus round-3 B3 raised, now in the replacement rule. *Fix:* Add the missing side conditions to §5.6 and to the §12 toggling_lemma witness check: X is disjoint from the borrowed set and from W's targets; every gate of V has its target in the borrowed set and all its controls in X (V touches no other wire); the sets of W's targets and W's controls are disjoint as sets (not merely per gate). With those four clauses the affine argument goes through and the counterexample is excluded because b2 is borrowed, hence not in X. Add the counterexample to suite F as a negative test for the witness checker.
- **[muse] B5_TARGET_SCHEMES_AND_LOG** (§8.1 expression AST, §8.3 gates/schemes/matching): Target expressions still cannot be evaluated identically by two parties. `log2inv_eps` has no definition: as a real log2(1/eps) it is generally irrational, contradicting exact-rational evaluation (suite E), and the grammar gives it an args list without arity. Scheme templates cannot be expanded: template wires are plain strings like 'c0' with no rule binding them to an actual gate's k controls, no indexed-wire syntax for a repeat body to reference c[i] or an aux wire, no statement of whether repeat's to bound is inclusive, no way to pass a gate parameter (an RZ decomposition needs theta/2), and no declaration of how many aux wires a scheme needs or of what class. 'First schemes entry' is also undefined because schemes is a JSON object. A vendor and a scheduler cannot produce the same gate sequence or the same cost from this format, which was codex B8 / muse B7 in substance. *Fix:* Define log2inv_eps as the exact integer min{k >= 0 : eps * 2^k >= 1} for 0 < eps <= 1 (load error outside), state each op's arity, and state that a table index outside the array is a load-time error. Replace free-form scheme wires with an indexed wire grammar: a scheme declares control wires c[0..k-1], one target t, optional parameter theta, and aux wires a[0..m-1] with m given by an expression in k; template gate entries are {gate, wires: indexed forms such as c[i], a[i+1], t, params: expressions over theta/k/i}; repeat is from-inclusive to-exclusive over integer i. Make `schemes` an ordered array (with a name field) so 'first' is defined, and state that a schedule's scheme reference resolves to that array entry. The restricted alternative — schemes only for fixed arity with fully explicit wires, one entry per k — is also implementable but cannot express MCX families, so take the indexed grammar.
- **[muse] B6_ENVELOPE_ORDERING_AND_SCC** (§9.2 identity/envelope/SCC, §16.3 hashing commentary): The semantic envelope is not byte-reproducible from §9.2's text. Part (5) says data entries and layout sub-entries are included 'sorted by name', without saying whether the two classes are merge-sorted by name or emitted as two sorted groups; a layout sub-entry has no 'JCS line' (the layout section is one object) — its `<dotted name> SP <JCS or INT>` line format appears only in Example 2's commentary; part (6) requires the hash of every referenced symbol, which is circular for an SCC member, and the SCC paragraph says intra-SCC 'references' are replaced by @$i without stating whether that replacement happens in part (6), or part (6) omits intra-SCC references, or includes a placeholder line; and which layout entries a symbol 'reaches' is judgement-based (@sum_db's envelope includes globals.zero, which its own body never addresses, but excludes the zero data line). Plausible readings give different hashes for the same object, so certificates and deduplication still do not interoperate in the general case. *Fix:* State the convention the examples in fact use (so the printed hashes stand): part (5) is two consecutive groups — first every reached data entry sorted by data name, written `NAME SP HEX LF`; then every reached layout sub-entry sorted by dotted name, written `<dotted name> SP <JCS encoding of its value> LF` (a scalar's JCS encoding is its decimal text). Move the layout sub-entry line format from the §16.3 commentary into §9.2. State that part (6) lists only references leaving the symbol's SCC, in first-reference order, each as 64-hex LF; intra-SCC references contribute no part-(6) line and are replaced by @$i in parts (4)-(5) wherever an @name token occurs. Define the reached layout set mechanically: the scalar fields H, A_tab, S_cells, null_size, heap_base; every globals entry (all of them initialise alloctab, matching @sum_db); and, for an oracle, its own interface_regions entries. I verified inc8 byte-for-byte under the printed rule and reproduced @sum/@sum_db only under the convention above, which is why it must be printed.
- **[muse] B7_CERTIFICATE_WITNESSES** (§12.1 claim kinds, §12.3 schema/composition, §6.4): The certificate still does not let an independent checker verify its numerical and some structural claims. A numerical claim's witness is `{"intervals": [...]}` with no statement of what the intervals enclose (matrix entries of what operator, in what basis order), how an operator-norm or diamond bound is derived from them, or how a checker 'recomputes' them without an algorithm — for diamond norm, an SDP optimum, no dual/feasibility witness format exists at all, so any array of numbers is an acceptable-looking 'proof'. Structural witness fields are given only for toggling_lemma; inverse_pair_library names no way to identify the library certificate it rests on. And `error` is a single {metric, value} per region although realised error depends on variant and inherited control count (the very keying §6.4 mandates for schedules and that cleanup entries have), so composition in §12.3 combines numbers that may belong to different variants. *Fix:* Make small-width numerical claims checker-computed rather than witness-trusted: state that for metric operator_norm the checker builds the realised and reference unitaries itself at the stated widths in interval arithmetic (basis order = allocation order, §14.2), forms interval enclosures of V-dagger U - I entrywise in row-major order, and derives the bound by the Frobenius-norm upper bound computed in interval arithmetic at precision_bits — the witness is then only {widths, precision_bits, bound} and is a checkable assertion about the recomputation, not data to trust. For metric diamond, either add an SDP dual-certificate schema (dual variable as an interval Hermitian matrix in stated order, with the PSD/feasibility checks the checker performs) or state that diamond numerical claims are evidence in this draft and only exhaustive/channel claims computed by the checker are proof; I recommend the evidence downgrade now and the dual schema as a named extension. Key `error` by '<variant>:<inherited_controls>' exactly as `cleanup` is keyed, and give the rule-specific witness fields for inverse_pair_library (the library entry's closure hash) and adjoint_table (no fields).
- **[muse] B8_SCHEDULE_SELECTOR_SEMANTICS** (§11 schedule document and obligations, suite H): The hierarchical schedule cannot yet be executed verbatim by two consumers. 'More specific entries override less specific ones' is a partial order: an entry specific in path and another specific in iteration can both match one generated operation with no stated winner, and document order is not declared significant or insignificant. `iteration` is undefined for the largest generated class — the B steps of an oracle and their prefix-reversal counterparts (does iteration count forward step t, reversed order, or loop repetitions of the source point?) — and `generated: gate` selects all gates a row expands to, although a single row expands to gates of different opcodes (dispatch comparators, arithmetic, exchanges) for which one scheme realisation cannot apply to all. A validator cannot tell whether such a schedule is legal, and two executors will realise, and charge, different circuits from it. *Fix:* Define specificity as a total order and conflicts as errors: an entry beats another if it is greater in the lexicographic tuple (path length, iteration non-*, phase non-*, generated non-*, kind-field present), and two incomparable maximal entries that both match one generated op make the schedule invalid (not first-wins, so encoder order is never semantic). Define iteration for every generated class: for a static point inside qloop, its 0-based dynamic repetition count within the invocation; for oracle-generated ops, the forward step index t in 1..B, with phase rev denoting the inversion of step t (executed in decreasing t); add an optional `generated_index` selecting the ordinal of the generated op within its source row's normative expansion, default '*', and require a gate entry whose realisation names a scheme to select only gates that scheme realises. State that an entry may instead be interpreted uniformly only when generated_index is '*'.
- **[muse] B9_UNCALL_INSTRUCTION** (§4.1 call/uncall/ret, §7.4 run history, §9.4, T4): The in-program `uncall` instruction (§4.1) has no operands and its only semantics is §7.4's 'reverses the most recent unreversed call whose frames are the top of the history'. After a call returns, any intervening instruction — including the copy of a result that is the usual reason to uncall — pushes a frame, so the call's frames are no longer the top; the spec does not say whether uncall then traps, faults, searches down the history for a segment, or is statically ill-formed, nor how the call's result instances (the call is both a 'defining instruction' frame and a 'call boundary' frame, with no stated order) are treated. Two executors will implement different machines, and a producer cannot know where uncall may legally appear. *Fix:* Choose one of two stated semantics. (a) Segment uncall, which I recommend if in-program reversal is wanted: form `uncall @f (args) (results)`; it finds the most recent unreversed call segment for @f whose recorded boundary args and produced results equal the current values of the named operands (all classical, so checkable), deletes that segment from the history reversing its memory/alloc/effect/Q-call frames exactly as in §10's tree, and leaves caller frames recorded after the segment (e.g. a copy of the result) in place; if no segment matches it is a CC trap / R fault record FAULT_UB_TRAP; executing uncall itself pushes a frame recording the segment id so whole-run reversal re-executes the call. (b) No in-program uncall: delete the instruction and state that call reversal exists only as the §10 run/tree operation and as LIFO trace reversal, renaming §9.4's convention accordingly. Either is defensible; (a) preserves the Janus-style compute-copy-uncall idiom the reversible tier will want, (b) is smaller. What cannot stand is an unlabelled pop with a silent precondition.
- **[opus] B1** (§3.7, §4.2, §16.3 example 2): Operand name resolution in lprocs is undefined, and example 2 depends on three unstated rules. (a) §3.7 says interface inputs are readable by 'any read operand of lifted rows', so in @sum the name `n` could mean the oracle's input `n` or @sum's parameter `n`. (b) @sum reads the oracle's location `base`, which is dynamic scoping into the enclosing oracle. That makes an lproc's meaning depend on which oracle links it, and its interface hash cannot capture it. Oracle interface inputs are pseudo-locations of the oracle body only. Anything else an lproc needs is passed as a parameter. Globals are then accessed only through explicit `lift.boundscheck` + `lift.load`/`lift.store`, and implicit global operands are ill-formed. - **[opus] B2** (§5.6 (toggling lemma), §12.1 structural witness): The side conditions do not stop V from writing non-borrowed wires, or from reading borrowed wires. Counterexample: V = `cx b x` (b borrowed), W = `cx x z`. Then X = ∅ (V XORs nothing into borrowed wires), W writes no wire of X, W's targets are outside X, the borrowed set and W's controls, and W has no borrowed control, so (i)–(iv) hold. Yet V;W;V⁻¹;W leaves z ⊕= b, an output entangled with the borrowed system, under a `structural` proof label. *Fix:* State the conditions as follows. (i′) V's targets ⊆ borrowed set B. V's controls ⊆ X, with X ∩ B = ∅, so V maps b ↦ b ⊕ v(X). (i″) W writes no wire of X. (ii) W's targets are disjoint from X, B, and every control of W. (iii) each W gate has at most one control in B. (iv) V⁻¹ is the exact reverse sequence of V. The conclusion is then that the net map is t ⊕= Σ_g c_g(Y)·v_{j(g)}(X), independent of b. Suite F checks (i′)–(iv) syntactically from the witness (V, W, X, B and the point range).
- **[opus] B3** (§3.3, §4.1, §4.7, §10): Per the north star, code that touches handles or measurement results runs in the device CC tier. Here, however, CC has no type for quantum-register ids, no instruction to allocate, free or slice a register, and no rule binding an n-qubit register to a `wire[n]`, `wire` or `region[A,W]` operand of `oracle_call`/`action_call`. Only the host can create registers (`bennett_qreg_new`). A program that calls `__bennett_qalloc` inside a loop, or that measures a register and then reallocates, has no ISA image, and two VMs would invent incompatible bindings. *Fix:* Add a CC type `qreg[n]` and these CC instructions: `q = qreg.new cls n` (clean), `qreg.free q` (the register MUST be clean; the simulator checks this and reports `E_QREG_NOT_CLEAN`; on hardware a non-clean free is a program error recorded in the run), `q2 = qreg.slice q lo len` (a borrow of the range for one call), and `qreg.concat`. Binding rule: a `qreg[n]` argument fills a `wire[n]` slot bit for bit. It fills a `region[A,W]` slot iff n = 2^A·W, with cell i = bits [iW, (i+1)W). `measure` consumes the qreg id. Register ids passed by the host get the same type. Add these operations to the run-history frames (§7.4) and to the reversal rules.
- **[opus] B4** (§8.3 schemes and matching): A scheme declares no op, control-count range or parameter signature that it realises, and no binding of its symbolic wire names (`c0`, `t`, the repeat index) to a gate's operands. It also cannot declare ancillae (clean or dirty, class, count as a function of k), although MCX decompositions need them. 'The first schemes entry whose template realises it' is therefore a unitary-equivalence question, not a matching rule. Two schedulers would pick different schemes and report different costs and frame requirements. *Fix:* Each scheme carries `realises: {op, controls: {min,max}, params}` and is matched exactly like a gate entry, first match in array order. Templates name wires `c{expr}` (i-th control, 0-based), `t`, `p{expr}` (parameter operands) and `a{expr}` (ancillae, declared in `ancillae: {count: expr, state: clean|dirty, class}`). `repeat` substitutes its variable into those subscripts. The template's correctness is the target author's obligation, checked by suite E (exhaustive T3 for permutation schemes, suite D for ε > 0). Scheme ancillae add to the frame descriptor (§9.4).
- **[opus] B5** (§9.2, §16.3): The identity rule and its worked examples disagree, so independent implementers cannot reproduce the hashes. §9.2 part (5) says 'the JCS line of that entry', but the example uses `<dotted name> SP <JCS or INT>` lines, a rule that appears nowhere normatively. Example 1 says 'the four function lines', but the canonical function bytes span six lines (header, regs, block label, three instructions). The final hash table prints each hash equal to itself, which is a template-substitution error. Example 2's layout also breaks §7.2's disjointness rule: the heap [32, 32 + 8160) contains db's mapping at [4096, 4112). Its stated depth fault 'depth_limit < n' is off by one, since n+1 nested calls occur. I could not execute a hash script in this environment to check the digests themselves. *Fix:* Put one byte-exact layout-entry encoding in §9.2. I recommend `<dotted path> SP <JCS value>` per scalar or object leaf, sorted by path in bytewise order. Delete the example's restatement. Correct the function-line count, print the hash table as `name = hash` with the full envelope bytes (hex or an escaped listing), and move the heap (e.g. heap_base = 4112) or db so that all ranges are disjoint.
