# How serious Julia compiler-packages are architected in 2026 — precedents for a Bennett.jl reimplementation

**Scope note on dates.** This report was written mid-August 2026, during/just after JuliaCon Global 2026 (Mainz, 10–15 Aug 2026). The installed baseline on the target machine is **Julia 1.12.5**; Julia **1.13** was at release-candidate stage (rc3, per Discourse) at time of writing — features below are marked MERGED (shipped in 1.12 or earlier, or confirmed in 1.13 rc) vs IN-PROGRESS/SPECULATIVE (nightly PRs, research papers, v0.1 placeholders) throughout.

## 1. The five projects, examined primary-source-first

### 1.1 GPUCompiler.jl — codegen interception via custom AbstractInterpreter + overlay method tables

GPUCompiler.jl (JuliaGPU, backs CUDA.jl/AMDGPU.jl/Metal.jl/oneAPI.jl) is explicitly **not for end users** — it is infrastructure other packages build on. Its architecture, read directly from `src/interface.jl` and `src/driver.jl` on `master`:

- A `CompilerJob{T,P}` bundles a `MethodInstance`, a `CompilerConfig{T,P}` (parameterized by an `AbstractCompilerTarget` and `AbstractCompilerParams`), and a `world` age — the unit of "one compilation."
- It runs a **custom `AbstractInterpreter`** (`GPUInterpreter`) during type inference, constructed with `method_table_view`, `owner` (cache owner), and custom `inf_params`/`opt_params`. This is the same public extension point Julia exposes for tools like JET.jl.
- Redirection of specific Julia methods (e.g. swapping in GPU-safe implementations of `Base` functions) is done via **overlay method tables** combined with a **world-age abuse**: overrides are registered in an otherwise-unreachable world, and a method-table view consults that world first, falling back to the normal table otherwise. GitHub source confirms this differs between Julia 1.6 (abusing world ~0–1) and 1.7+ (a distinct method-table-view mechanism).
- After inference, GPUCompiler calls into Julia's **own** `irgen()`/codegen (`compile()` → `emit_llvm()` → `irgen()`) to get an LLVM module — it does **not** reimplement Julia-to-LLVM lowering. It then post-processes that LLVM module (`prepare_job!`, `link_libraries!`, `finish_module!`, `optimize_module!`) and hands it to LLVM's own backend (`mcgen()`) for a target other than the host (e.g. NVPTX).
- **Stability track record is poor by design.** The world-age/overlay-table trick is explicitly a hack on internal machinery: `julia` issue #44174 ("Purity modeling broke overlay tables") shows a compiler-internal change breaking it outright; GPUCompiler PR #151 shows the maintainers shipping *version-conditional* code paths (1.6 vs 1.7+) to keep the trick working. This is maintained continuously by engineers embedded with Julia core (Tim Besard/maleadt), a cost structure a downstream, non-core-adjacent project is unlikely to sustain.

Sources: [GPUCompiler.jl repo](https://github.com/JuliaGPU/GPUCompiler.jl), [`interface.jl`](https://github.com/JuliaGPU/GPUCompiler.jl/blob/master/src/interface.jl), [`driver.jl`](https://github.com/JuliaGPU/GPUCompiler.jl/blob/master/src/driver.jl), [PR #151 (1.6/1.7 method overrides)](https://github.com/JuliaGPU/GPUCompiler.jl/pull/151), [julia#44174](https://github.com/JuliaLang/julia/issues/44174).

### 1.2 Enzyme.jl — LLVM-level transform (closest existing kin to Bennett.jl's own approach)

Enzyme.jl binds the (language-agnostic, C++) Enzyme AD engine, which differentiates **optimized LLVM IR directly** — it is neither source-to-source nor a runtime tape. Julia lowers to LLVM IR, Julia's own optimizer runs, and Enzyme then does activity/type analysis over that already-optimized SSA stream and emits an adjoint. This is architecturally the **same substrate choice Bennett.jl already made** (act on LLVM IR, after Julia's codegen, not before it), just for a different transform (derivative generation vs. gate lowering). Enzyme.jl is widely regarded as the most mature "operate on Julia's real LLVM IR" project in the ecosystem, which is direct, if indirect, validation of option (a) below.

Sources: [Enzyme.jl](https://github.com/EnzymeAD/Enzyme.jl), [Enzyme.jl docs](https://enzymead.github.io/Enzyme.jl/stable/), [Enzyme AD project](https://enzyme.mit.edu/).

### 1.3 Reactant.jl — MLIR/XLA tracing, and why pure tracing is now known to be insufficient

Reactant.jl traces Julia functions into MLIR (then XLA) using two wrapper array types, `ConcreteRArray` (real data) and `TracedRArray` (symbolic placeholder). Per its own docs: *"[Reactant] presently operates as a tracing system. Compiled functions will assume the same control flow pattern as was originally taken by objects used at compile time, and control flow (e.g. if, for) as well as any type instabilities will be removed."* Control-flow decisions that depend on non-`ConcreteRArray` data simply do not propagate into the compiled function at all.

This is the textbook single-path tracing failure mode, and the Reactant/Enzyme team has now published a fix-in-progress: **"Control-flow Aware MLIR Tracing"**, 36th International Workshop on Rapid System Prototyping (RSP), Oct 2025 ([DOI 10.1145/3768617.3770735](https://doi.org/10.1145/3768617.3770735), [HAL preprint hal-05304199](https://hal.science/hal-05304199v1/document)). Its abstract states the paper "proposes enhancing the Reactant tracing system **by integrating the Julia compiler['s] static analysis**" — i.e., the fix for tracing's control-flow blindness is to reintroduce real compiler-level CFG analysis (the `Core.Compiler`/LLVM-IR route), not to push tracing harder. As of writing this is a recent workshop paper, **not** a shipped, stable Reactant feature — IN-PROGRESS/SPECULATIVE, not MERGED.

Sources: [Reactant.jl repo](https://github.com/EnzymeAD/Reactant.jl), [Reactant.jl docs](https://enzymead.github.io/Reactant.jl/stable/), [Reactant control-flow discussion](https://discourse.julialang.org/t/using-control-flow-in-reactant/131946), [Control-flow Aware MLIR Tracing (ACM DL)](https://dl.acm.org/doi/10.1145/3768617.3770735).

### 1.4 Mooncake.jl — typed `IRCode`-level transform via `Core.Compiler`

Mooncake.jl (AD, chalk-lab, formerly compintell) operates on `Core.Compiler.IRCode` — the typed SSA-form IR Julia's own optimizer works on, one stage *before* LLVM IR. Because `IRCode` gets restructured heavily during a transform pass (blocks inserted/removed), Mooncake wraps it in a parallel structure, `BBCode`, that adds stable names to every line/block so edits survive re-linearization.

Stability evidence, straight from the repo: open PRs exist to add **Julia 1.12 compatibility**, **nightly/1.13 support**, and **1.14 Compiler-API changes**, each requiring nontrivial patchwork to `BBCode`/IR-infrastructure internals per Julia version. This confirms `Core.Compiler.IRCode` is *not* a frozen public API either — but the churn is narrower and more mechanically discoverable (named struct fields, documented-ish internals) than raw LLVM textual/structural drift, and Mooncake's maintainers treat "port to new Julia" as routine, bounded work rather than a crisis.

Sources: [Mooncake.jl repo](https://github.com/chalk-lab/Mooncake.jl), [README](https://github.com/chalk-lab/Mooncake.jl/blob/main/README.md), [Internal Design discussion #136](https://github.com/chalk-lab/Mooncake.jl/discussions/136), [PR #714 (1.12 compat)](https://github.com/chalk-lab/Mooncake.jl/pull/714).

### 1.5 The `Compiler` stdlib package — MERGED (v0.1) but explicitly a placeholder

Since Julia 1.12, `Core.Compiler`'s functionality is also exposed as an installable stdlib named **`Compiler`**, allowing a project to `Pkg.add`/`dev` an alternate or pinned compiler implementation and switch to it via `InteractiveUtils.@activate Compiler`. Its own docs are explicit about maturity: *"The reason for providing this placeholder version is to minimize compatibility issues between the `Compiler` standard library, the Julia runtime system, and dependent packages **until proper versioning for the `Compiler` stdlib is in place**."* v0.1 simply re-exports `Base.Compiler` under a new name; "switching compiler implementations natively" is supported from 1.12 onward, but there is no independent-versioning guarantee yet as of Aug 2026 (rc3 of 1.13 still ships v0.1-class semantics). This is the ecosystem's own acknowledgment that decoupling `Core.Compiler` from the Julia runtime release cycle is a known, wanted, **but not yet delivered** goal — treat option (b) below as "improving, immature."

Sources: [`Compiler.jl` docs (JuliaHub mirror)](https://docs.juliahub.com/General/Compiler/stable/), [`BaseCompiler.jl`](https://github.com/JuliaLang/BaseCompiler.jl), [Julia repo `/Compiler` directory](https://github.com/JuliaLang/julia/tree/master/Compiler).

### 1.6 juliac / `--trim` — MERGED (1.12 experimental) — deployment, not extraction

`--trim` (via `JuliaC.jl`) does whole-program static analysis to strip unreachable code from a system image, shrinking a demo executable from 205MB to 1.7MB. It requires that everything reachable from the declared entrypoints be **free of dynamic dispatch**, or trimming is unsafe and errors at compile time. This is orthogonal to Bennett.jl's IR-extraction substrate question (it's a *deployment* tool, not a code-generation-interception mechanism) but is worth noting as corroborating evidence: the Julia core team is independently converging on "fully-inferred, monomorphic, no-dynamic-dispatch" as the shape a Julia program must have before serious static tooling can act on it reliably — exactly the assumption Bennett.jl already imposes (`optimize=false`, fixed bit-widths, no dynamic dispatch reachable in a compiled function).

Sources: [Julia 1.12 Highlights](https://julialang.org/blog/2025/10/julia-1.12-highlights/), [JuliaC.jl](https://github.com/JuliaLang/JuliaC.jl), [`--trim` I/O bug #58458](https://github.com/JuliaLang/julia/issues/58458).

### 1.7 Adjacent/newer precedent: Hardware.jl (Julia → MLIR high-level synthesis)

`Hardware.jl` (Cornell CAPRA group, arXiv:2503.09463, "work in progress") is the closest domain match to Bennett.jl in the literature: it compiles plain Julia to *hardware* (via MLIR) rather than to a numeric kernel. It uses Julia's `AbstractInterpreter` framework to statically trace/analyze code without executing it, explicitly generates SSA phi nodes to represent control-flow merges, and converts loops into explicit unrolled/pipelined hardware constructs — the same "unroll, don't loop" and "resolve phi into explicit merge logic" moves Bennett.jl's own `lowering/cfg.jl` and `lowering/phi.jl` already make. Its stated limitations (dynamic memory, Julia's flexible type system vs. fixed hardware, no support for runtime-dependent control flow) mirror Bennett.jl's own constraints almost exactly. It is a second independent data point that the "AbstractInterpreter as the front door, phi-node-preserving lowering as the internal representation" pattern is the field's converging answer for Julia-to-circuit compilation, not just Bennett.jl's own choice in isolation.

Source: [Hardware.jl paper, arXiv:2503.09463](https://arxiv.org/pdf/2503.09463) (also mirrored at [capra.cs.cornell.edu](https://capra.cs.cornell.edu/latte25/paper/5.pdf)).

### 1.8 JuliaCon 2026 (Mainz, 10–15 Aug 2026)

No talk in the 2026 program was found specifically on reversible/quantum circuit compilation from Julia. The nearest compiler-tooling talk found is **JETLS** ("Bringing Julia's runtime into language-server analysis," aviatesk) — a language server built on "byte-precise lowering and abstract interpretation," reusing Julia's own macro handling and type inference for editor tooling. It's evidence that `AbstractInterpreter`-based static analysis (option (c)/(b) territory) is an actively growing genre for *tooling*, distinct from but related to compiler-transform use cases. No 2026-vintage successor to LLVM.jl, GPUCompiler.jl, Mooncake.jl, or Reactant.jl was found; the field's architecture space, as of this writing, is the four already covered above, plus IRCode/Compiler-stdlib maturation as the main forward motion.

Sources: [JuliaCon 2026 site](https://juliacon.org/2026/), [JETLS talk](https://pretalx.com/juliacon-2026/talk/QLXWSB/).

## 2. The tradeoffs table (centerpiece)

Substrate options for a from-scratch reversible-circuit compiler, scored **Low/Med/High** (High = favorable) on five axes. Justification for each cell is grounded in §1 and, where marked †, in Bennett.jl's own prior internal research (see §3).

| Substrate | Stability across Julia versions | Coverage of plain-Julia semantics | Control-flow fidelity (loops/phi) | Effort | Debuggability |
|---|---|---|---|---|---|
| **(a) LLVM IR via LLVM.jl** (status quo) | **Med.** LLVM C API itself is back-compat-stable; the *Julia-generated IR content* drifts across releases (CLAUDE.md Rule 5 already institutionalizes this) and LLVM.jl requires recompilation whenever Julia bumps its bundled LLVM. Real but bounded, mechanical churn. | **High.** Everything Julia can run eventually becomes LLVM IR — no semantic gap, at the cost of low-level ABI noise (sret, byval, GC barriers) that must be handled explicitly. | **High.** Full CFG with real `phi` nodes for every path is the substrate's native form — exactly what Bennett needs for MUX synthesis. | **Med** (rewrite) / **sunk** (current). ~2.7k+2.9k LOC already exists and works; a rewrite still needs full aggregate/sret/intrinsic/GC handling. | **Med.** `code_llvm`/`print_circuit`-style text dumps are inspectable without extra tooling, but optimizer artifacts obscure Julia-level intent. |
| **(b) Typed `IRCode` via `Compiler` stdlib** | **Low→improving.** `IRCode` itself changes every release (Mooncake needs dedicated 1.12/1.13/1.14 PRs); the new `Compiler` stdlib (2026, v0.1) is *designed* to eventually decouple this but is explicitly a "placeholder…until proper versioning is in place" — not yet delivered. | **High for Julia-native ops, narrower than LLVM for ABI-level detail.** Sits one stage above LLVM: no sret/byval/GC-barrier synthesis to fight, but still-boxed/`Any`-typed paths for anything not fully inferred, same as today. | **High.** `IRCode` has explicit basic blocks, `GotoIfNot`, `PhiNode` — structurally isomorphic to what Bennett already resolves at the LLVM layer; arguably easier to read (named blocks) via `BBCode`-style wrapping (Mooncake's proven pattern). | **Med-High.** Different node types than LLVM IR — extraction and much of lowering would be rewritten — but *less* total code since ABI-level struct-splitting/GC lowering disappears. | **High.** `Base.code_ircode` prints cleanly in the REPL with source line info; no LLVM toolchain needed to inspect. |
| **(c) GPUCompiler-style pipeline hooks** (custom `AbstractInterpreter` + overlay method tables, still emitting real LLVM via Julia's own `irgen`) | **Low.** Built directly on the most volatile internal seams (world-age abuse, method-table views); historically broken by an unrelated Julia-core change (purity modeling, julia#44174); requires continuous co-maintenance with Julia core to track. | **High**, plus a genuine win: overlay method tables are a principled, Julia-native replacement for Bennett's current hand-rolled `register_callee!`/`_lookup_callee` registry (`src/extract/callees.jl`). | **High** (same LLVM CFG as (a)). | **High.** Either depend on GPUCompiler.jl itself (explicitly "not for end users," heavy, GPU-target-shaped) or reimplement its world-age/overlay-table hacks from scratch — Bennett's own 2026 design docs already rejected it once as a "new heavy dependency… would change IR shape" (†). | **Med.** Same LLVM-level inspection as (a), plus an extra layer of overlay-table indirection to reason about. |
| **(d) MLIR/tracing (Reactant-style)** | **Med for MLIR itself** (a genuinely stable, versioned, well-documented IR framework — arguably better specified than raw LLVM textual IR or `IRCode`), **Low for the Julia-side tracing mechanism** that feeds it. | **Med**, and unproven outside array/ML workloads — no existing MLIR dialect for classical reversible-gate synthesis; would require authoring one from scratch. | **Low as pure tracing** — Reactant's own docs concede `if`/`for` are "removed," single concrete path only; a 2025 paper exists *because* this was recognized as insufficient, and its fix reintroduces real compiler static analysis (folding back toward (a)/(b)). | **Very high.** Heavy toolchain (XLA/PJRT-class binary deps), *and* a bespoke gate-synthesis MLIR dialect with no off-the-shelf starting point. | **Med.** Excellent MLIR-native verification/pretty-printing, undercut by an extra tracing/wrapper-type indirection layer of its own. |
| **(e) Operator-overloading / tracing DSL** (Cassette/IRTools-style contextual dispatch, or bespoke value-wrapper that accretes gates as it flows through plain Julia) | **High w.r.t. Julia internals** (pure multiple dispatch, touches no compiler internals at all) but the leading example, Cassette.jl, is legacy/effectively superseded. | **Low-Med.** Only sees operations that actually execute for one concrete run — exactly Reactant's single-path problem, without even MLIR's verifier as a backstop. | **Low — actively disqualifying for Bennett.** This is the precise failure mode CLAUDE.md's phi-resolution rules exist to prevent: Bennett's core task is compiling *both* branches of an `if` into a MUX; a trace sees only the branch taken at trace time and would be **silently wrong**, not crash-loud — a direct violation of Rule 1 (fail fast, fail loud). | **Low** to prototype, **High** to reach correctness parity (would need to reimplement full symbolic/path-condition tracking, i.e. re-derive (a)/(b) from inside a weaker starting point). | **High** for prototyping (pure Julia stack traces), **Low** for correctness confidence (bugs are silent, not loud). |

† = corroborated by Bennett.jl's own prior internal research: `docs/design/40ys/proposal_A.md:187-189` explicitly rejected `Base.code_typed_by_type`/`code_ircode_by_type` ("Typed IR, not LLVM IR… Rejected") and GPUCompiler.jl ("New heavy dependency, different `CodegenParams`; would change IR shape and hence gate-count baselines. Rejected.") when investigating an sret-lowering bug in 2026. That was a narrower question (how to fix one extraction bug, with gate-count regression baselines to preserve) than "what substrate for a ground-up rewrite," but the underlying architectural tradeoffs are the same ones this report re-derives independently from 2026 ecosystem evidence — and reach the same conclusion.

## 3. Relevance to Bennett.jl

**The status quo (a) is not merely legacy inertia — it is the substrate every serious "transform real Julia programs" project in the ecosystem either uses directly (Enzyme.jl) or eventually falls back toward when a lighter-weight alternative's control-flow blindness bites (Reactant/MLIR's 2025 "control-flow aware" patch, which re-imports Julia compiler static analysis).** For a reversible-circuit compiler specifically, control-flow fidelity is not a nice-to-have axis among several — it is close to lexicographically first. Bennett's entire hard-problem surface (CLAUDE.md's phi-resolution section, "false-path sensitization," the v0.5 soft-float overflow bug) exists *because* the compiler correctly sees every branch and must synthesize correct MUX logic for it. Any substrate that doesn't reliably expose the full CFG (tracing DSLs, naive MLIR tracing) doesn't just make Bennett's job harder — it removes the ability to detect its own worst bug class, replacing loud phi-resolution crashes with silent wrong answers. That is disqualifying under Rule 1 (fail fast, fail loud), independent of engineering effort.

**Genuine 2026 news for a from-scratch reimplementation is option (b), not options (c)–(e).** The `Compiler` stdlib package is a real, if immature, attempt by Julia core to do exactly what Bennett would want: pin/version the typed-IR layer independent of the Julia runtime. It is not ready today (v0.1 placeholder, no independent versioning), but a ground-up rewrite targeting Julia 1.13+ should treat `Core.Compiler.IRCode` (accessed via the `Compiler` stdlib, with a `BBCode`-style stable-naming wrapper modeled on Mooncake's proven approach) as a serious contender for *simplifying* the extraction layer — moving Bennett's frontier from "walk textual/structural LLVM IR and fight sret/byval/GC-barrier ABI noise" to "walk typed SSA IR that is structurally closer to what the Julia programmer wrote," at the cost of taking on `IRCode`'s own (better-bounded, per Mooncake's experience) version churn instead of LLVM's.

**The overlay-method-table pattern from GPUCompiler.jl (option (c)) is worth stealing narrowly even if the LLVM-extraction substrate is kept.** Bennett's existing `src/extract/callees.jl` registry (`register_callee!`/`_lookup_callee`) solves the same problem GPUCompiler's overlay tables solve — redirecting specific Julia functions (in Bennett's case, `soft_*` division/memory primitives) to alternate implementations during compilation — by hand, with a bespoke cache. Depending on GPUCompiler.jl itself was already correctly rejected (§2, †); but its *pattern*, reimplemented narrowly and without the fragile world-age abuse, could replace or complement the current registry with something more systematic, without inheriting GPUCompiler's version-fragility (since Bennett would only borrow the *idea*, not the world-age hack itself).

**MLIR/tracing (d) and operator-overloading (e) should both be ruled out as primary substrates for Bennett.** Not because MLIR or Julia-native tracing are bad technology in general (Reactant is a serious, well-funded, actively developed project) — but because their core mechanism (concrete-value tracing that sees one branch per run) is structurally incompatible with what a reversible-circuit compiler must do (see every branch, always). The ecosystem's own most sophisticated tracing project has, as of late 2025, independently concluded it needs to bolt real compiler static analysis back on to fix exactly this gap — which is strong third-party validation that Bennett should not go the other direction.

**juliac/`--trim` (§1.6) is orthogonal but validates an existing constraint.** It's a deployment tool, not an extraction substrate, but its "no dynamic dispatch reachable from entrypoints" safety requirement for `--trim=safe` independently validates the fully-monomorphic, `optimize=false`, fixed-bit-width discipline Bennett.jl's pipeline already imposes on the functions it compiles (`reversible_compile(f, Int8)` etc.) — worth keeping as an explicit invariant if starting fresh, and possibly worth revisiting whether a rewritten Bennett could itself ship as a `--trim`-compiled standalone tool for deployment (a separate, later question from substrate choice).

## 4. Bottom line for the "assume codegen is free" reimplementation question

If code-generation effort is genuinely not the constraint, the highest-value place to spend that freed-up effort is **not** switching substrates away from LLVM IR — none of (c), (d), (e) beat (a) on the axis that matters most (control-flow fidelity), and (b) is a live contender only once the `Compiler` stdlib matures past its 2026 v0.1 placeholder state, which is a bet on future Julia-core delivery, not a today-ready design. The higher-value use of "codegen is free" is investing directly in what (a) is currently weakest at: hardening `ir_extract.jl` against LLVM-IR-shape drift (Rule 5 is already a scar from this) via a more systematic pattern-matching layer over the C-API walk, and evaluating `IRCode`-based extraction as a parallel, lower-ABI-noise front end to compare against — worth a scoped research spike, not a full substrate swap, before Julia's `Compiler` stdlib is versioned properly.
