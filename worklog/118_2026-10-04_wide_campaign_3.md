- `Base._methods_by_ftype` returns an EMPTY list, not `nothing`, for both "no method" and "ambiguous
  concrete call"; the old code mapped empty to `nothing` and skipped. Abstract signatures and
  builtins return a method list (never `nothing`).
- Both typings with no method: still skipped (both throw at the same call; an unconditional
  instance is refused earlier by `_check_softfloat_result` "always throws").
- The worker executed the two hgya leftovers. (a) Dispatch queries (`hasmethod`, `applicable`, also
  via `Fix1` and on Union-typed arguments): already refused, no miscompile. (b) **A non-concrete
  call inside a Base forwarder MISCOMPILES:** `hb_d(x::Float64) = signbit(x); hb_d(x) =
  !signbit(x); hb_u(x::Int) = false; hb_u(x) = hb_d(x); fb(x) = (y = signbit(x) ? 1 : x;

  not descend, and the non-concrete check is gated by `user &&`. Filed Bennett-72xf (P1), assigned.
  hgya closed: every other item on it is fixed or refused.

**Bennett-1qws — `llvm.floor` / `ceil` / `trunc` / `rint` on f64 are dispatched**
(`_handle_intrinsic`). They lower to `IRCall` on `soft_floor` / `soft_ceil` / `soft_trunc` /
`soft_round`; any other width is an `_ir_error`. `rint` is taken as round-to-nearest, ties to even
(the circuit has no FP environment); `soft_round` IS the banker's-rounding primitive
(`llvm.roundeven` already uses it; `llvm.round`, ties away, maps to `soft_round_away`). Landing
logs: 1qws 616/616, mq6f 7367, gate baselines 39.
- Plain Julia was affected more widely than the bead said: `round(x, RoundNearest)` emits
  `llvm.rint` and `round(x, RoundNearestTiesAway)` emits `llvm.trunc`, so both were uncompilable on
  Float64 through the Int64-reinterpret route.
- The stale comment claimed the callee registry would pick these intrinsics up. It could not: the
  registry is keyed on `soft_*` names, not `llvm.*` names.

| callable | `:expression` | `:tabulate` |
|---|---|---|
| callable `Ptr` | `[8]`, all 256 inputs wrong (c(1) = −95, native 4), verifies | correct until the pointee changes, then frozen |

- **The orchestrator's guess was wrong:** the brief said "I expect the callable-primitive-integer
  case to be wrong today in the same way as the pointer". It was not — the byte serialiser keys on
  `sizeof`, so callable integers were already bound correctly. Only `Ptr` was unsound.
- **Second unsound bug, found by the red run:** `_parsed_ir_cache` (Bennett-4ddk, 2026-10-03) was a
  `Dict` keyed on `f`. `isequal` equates `Int8(0)`, `UInt64(0)`, `0.0` and `false`, so compiling the
  callable `false` after the callable `Int8(0)` silently returned the other's IR (`x + 0` instead
  of `x − 1`), and likewise for every equal-valued pair. Now an `IdDict` (keys compared by `===`),
  same 5-tuple key shape, so `test_ej4n`'s pin stands. Reach: callables that are themselves numbers
  (closure and `Fix` structs of different types were never `isequal`). **Any cache keyed on a user
  VALUE must use egality, not `isequal`.**
- On Julia 1.12 `sizeof(F24)` is 4, not 3: the 3-byte field is padded, `dereferenceable(4)`. The
  buffer already used `sizeof(T)` + `fieldoffset`, so no layout change was needed.
- String, Symbol and mutable fieldless callables used to pass `fieldcount == 0` and then die on
  `sizeof(String)` or be accepted; they now get the clean ArgumentError.
- Step 4 of the brief (replay everything the helpers deleted by 2op8 used to refuse): the only
  regression was the callable `Ptr` / `LLVMPtr`; a mutable fieldless struct had also become
  accepted and is refused again. One deliberate 2op8 relaxation stays: an immutable struct whose
  only field is `Type{X}` is bound on `:tabulate` (was refused before 2op8) — sound.

## Session log — 2026-10-04 — bie9 second half landed (d9fe058): lowering was QUADRATIC in gate count (sizehint! shrinks since Julia 1.11); `^` compiles; sl4h decision revised to a hybrid

**The stall was not the division loop.** The orchestrator's brief offered three hypotheses and
favoured (a), the inlined `soft_fdiv` loop unrolled 64 times. The worker profiled first (sampling
profile with a hard stop, as briefed) and found (b): about 80 % of samples during `lower` were
`GenericMemory` allocation, reached from `push!` in `multiplier.jl` and from `sizehint!` in
`lower_add!`.
- Cause: the add / sub / mul emitters begin with `sizehint!(gates, length(gates) + k)`. Since
  Julia 1.11 `sizehint!` SHRINKS by default (`shrink=true`), so on a vector whose capacity already
  exceeds `length + k` (push!'s geometric slack, or a multiplier's larger hint) it reallocates DOWN
  to exactly `length + k` and copies the whole gate vector; the next `push!` grows it again. One
  full copy per arithmetic operation: lowering was O(total gates) per add / multiply.
- The hints came in with Bennett-5kio / U109, so this slowed EVERY large compile, not only `^`.
- Fix: `_grow_hint!(v, n) = sizehint!(v, n; shrink=false)` (`src/adder.jl`; a no-op on
  Julia < 1.11), used at the five sites in `adder.jl` (×3), `multiplier.jl`, `qcla.jl`. No other
  bare `sizehint!` remains in the emitters or `src/lowering/` (orchestrator grep); the ones in
  `compose`, `controlled`, `bennett_transform`, `eager`, `value_eager`, `instructions.jl` are
  one-time hints on fresh vectors.
- Emitted gates are unchanged: 39 gate-count baselines identical. Landing logs (rebased tree):
  compile test 270 + 28 (72.5 s), extract 2/2, softfpow_julia 331/331, gate baselines 39/39.
- Worker's microbench of the old pattern: 1.1 / 5.7 / 21 s at n = 2k / 4k / 8k operations against
  about 0.01 s with the fix. `lower` on the `^` wrapper: not finished at 150 s before, 20.4 s after.
- **Not measured: what this does to the suite.** The full-suite run later today is the first
  before/after data point (2026-10-03: 61 min serial, 19.5 min in ten shards).

**`^(Float64, Float64)` compiles** (with `max_loop_iterations=64`): 28,847,211 gates, 6,632,488
Toffoli, 17,156,850 wires, about 52 s (23 extract + 20 lower + 9 bennett); 24 inputs bit-equal to
`Base.:^` plus `verify_reversibility`. The wrapper's ParsedIR is small next to its circuit: 19
blocks, 20,411 instructions, 6 phis, calls to `soft_fmul` ×102 and `soft_fadd` ×61, one self-loop

costs about 4× the gates and 4.4× the Toffolis.** Closed bie9; filed vwax (out-of-line `soft_fdiv`

- The new compile test clears the compile cache at its end so the 28.8M-gate circuit does not stay
  in memory for the rest of the suite (3.5 GB peak for the file).
- `test_softfdiv.jl` and `test_emv_llvm_pow_dispatch.jl` have no `using Test` (Bennett-guj0).
- **Bennett-armp, recommendation changed:** with bie9 fixed, routing `llvm.pow` through
  `soft_pow_julia` is possible, and the orchestrator now recommends against it. Julia-source `x^y`
  on Float64 already dispatches to `soft_pow_julia` and is bit-exact; `llvm.pow` is what C / Rust
  IR carries, where libm (which `soft_pow` ports) is the natural reference; the port is 4× the size;
  and 1–2 ULP vs Base is inside the documented ≤2 ULP contract (v4iy). What is out of contract is
  5mt5's 14-ULP case. Recorded on armp; it waits on the maintainer's ruling on v4iy.

**Lesson for briefs.** A hypothesis in a brief anchors the worker; this one was explicitly marked
as a hypothesis with "verify it" and a measure-first order (size table, phase timings, profile with
a hard stop), and the worker reported "your hypothesis (a) was wrong". Keep that shape for any
performance bead: sizes, phase timings, a bounded profile, THEN a fix.

**Bennett-sl4h — decision revised a second time, on the worker's data.** The "always narrow the
unoptimised IR" worker stopped on the brief's STOP condition and did not land (WIP a7ec7d6, local
branch `work/sl4h`). Its numbers: 804 cells (134 programs × {Int8, UInt8} × W ∈ {2,3,4,6,7,8}) with
0 accepted-and-wrong and the `x*16 == 0` witness fixed — but the koi8 corpus at `optimize=true`,
W < 8 drops from 593 accepted to 460 (300 correct cells lost, 167 gained), and the losses are the
commonest Julia spellings:
- `x == 5` with an untyped literal, `iseven(x)`, UInt8 `x > 2`, `Int8(x == 5 ? 1 : 0)`: the
  unoptimised IR keeps Julia's promotion (`sext` / `zext` i8 → i64, or an i64 phi), refused by the
  allowlist as "a second data domain".
- Int8 `x >> 1`: the unoptimised IR keeps the overshift arm `ashr x, 7` (7 > W).
- The lost corpus cells mostly mention a literal that does not fit in W bits which the optimiser
  had folded away; the exception is UInt8 `x >= 2^(W-1)` (6p8j allows unsigned constants only in
  `0 .. 2^(W-1)-1`).
- Optimised narrowing was not wrong on any cell of that corpus; the known wrong case is the
  separate residual testset.

Adopted instead: **hybrid** — with `bit_width` set and `optimize=true`, try the unoptimised IR
first and use it when extraction + narrowing accept it; otherwise fall back to today's optimised
path with its koi8 checks. Nothing that narrows today is lost, the pinned witness is fixed, the 167
cells are gained. It is NOT a full fix: a program whose unoptimised IR is refused and whose
optimised IR holds an S-bit-fact fold can still be accepted wrongly, as today, so sl4h stays open
(P2) after it lands. Full closure is three allowlist extensions (the promotion idiom, the overshift
guard, the 6p8j unsigned range) and then dropping the fallback — or V2-PRD D0. 3d1k is not
superseded.
- The first revision of this decision was made from one test comment ("unoptimised IR narrows the
  source's own multiply and is right") without measuring what else the unoptimised IR contains. The
  STOP clause in the brief ("if ordinary Int8 programs stop compiling, do not land") is what kept
  it off main. Put a measurable stop condition in any brief that implements an orchestrator
  decision.
