# Worklog chunk 089

## Session log — 2026-06-23 — Bennett-beaw: ConstantPointerNull → zero cell under ptr_cells

**CW-D lever.** Model a `ptr null` (LLVM `ConstantPointerNull`) operand as a
zero 64-bit VM cell under the closed-world `ptr_cells=true` gate. A null pointer
is address 0 and a pointer is one Int64 VM cell (ADR 0018 §A), so `ptr null` →
`iconst(0)` (`ConstOperand(0)`) at width 64. On the circuit path
(`ptr_cells=false`) it stays FAIL-LOUD — the Bennett-bjdg / U80 behaviour,
byte-identical. The circuit/:heap models have no canonical zero-cell pointer
semantics, so the null→0 modeling is strictly gated.

This is the fdict-root successor wall past iwo9 (type-tag round-trip) and r92o
(gc_alloc_obj). Pre-fix, the real `fdict_d1b(a,b) = (d=Dict{Int8,Int8}();
d[a]=b; d[a])` root walled (optimize=false, ptr_cells=true) verbatim at:

> ir_extract.jl: ConstantPointerNull operand: ptr null — null-pointer
> dereference. Bennett.jl does not currently lower null-pointer operands.
> (Bennett-bjdg / U80)

from the `store ptr null, ptr %obj` field-inits in the inlined
setindex!/getindex body.

### _operand-threading approach (minimal, mechanical)

`_operand(val::LLVM.Value, names)` is a HOT path with ~80 call sites across
`src/extract/*.jl` — threading a positional/required `ptr_cells` everywhere
would be a huge, risky diff. Instead: added a **defaulted kwarg**
`ptr_cells::Bool=false` to the `LLVM.Value` method ONLY. Every existing call
site compiles against the same method and is byte-identical (default false →
the U80 fail-loud for null still fires). Only the TWO ptr_cells-gated call
sites that can actually receive a `ptr null` pass `ptr_cells=true`:

1. `src/extract/instructions.jl` — the `ret` arm (the `ptr_cells && ... isa
   PointerType` branch): `IRRet(_operand(ops[1], names; ptr_cells=true), 64)`
   — handles `ret ptr null`.
2. `src/extract/instructions.jl` — the `store` arm (the `ptr_cells && vt isa
   PointerType` branch): `IRStore(ssa(...), _operand(val, names;
   ptr_cells=true), 64)` — handles `store ptr null, ptr %obj`.

The `_VectorLaneValue` overload of `_operand` (vectors.jl:69) is NOT touched —
it's a separate method on a non-`LLVM.Value` type and the vector lane path never
carries a `ptr null`. No conflict.

The model itself lives in `src/extract/helpers.jl` `_operand`, in the precise
`LLVMConstantPointerNullValueKind` arm (the value-kind C-API check, NOT a
Julia-level type — LLVM.jl doesn't expose one; Rule 5). Added `ptr_cells &&
return iconst(0)` BEFORE the U80 `error(...)`. Critically left
ConstantFP / PoisonValue / UndefValue arms UNTOUCHED — they are NOT null
pointers and have no canonical zero-cell meaning, so they stay fail-loud under
BOTH gates.
