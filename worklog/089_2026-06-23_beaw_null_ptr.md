## Session log — 2026-06-23 — Bennett-37ib: de-list JET from test target → restore green Pkg.test (689016 assertions)

**Orchestrated fix** (Opus implementer + orchestrator as +1 reviewer). The canonical
gate `julia --project -e 'using Pkg; Pkg.test()'` had been aborting at **TEST-ENV
PRECOMPILATION** — so Bennett's own ~688k-assertion correctness suite never ran. This
was the precondition blocker for all core-pipeline work (e.g. the vbv9 fdict-frontier
3+1), so it was done first.

**The non-obvious gotcha (write this down):** `Pkg.test()` precompiles the *entire*
test environment — the package PLUS every `[targets].test` extra — **before a single
test file executes**. So if a test-only extra crashes/hangs during precompile, it
aborts the WHOLE suite at setup, and **gating the offending test *file* cannot help**
(the dep is precompiled before any file runs). The only robust fix is to take the dep
OUT of the test target.

**Root cause:** JET 0.11.3 **HANGS** (not crashes) precompiling under the strict
test-config flags (`--check-bounds=yes --warn-overwrite=yes ...`) on this machine —
observed 14.5 min wall / <1 min CPU, no `.ji`/`.o` produced. Subtlety that masked it:
a standalone `using JET` *succeeds* (loads off a stale global-depot `.ji`, even returns
90 reports), but the fresh strict test-env precompile does not. JET was also missing
from `Manifest.toml` (it's a test-only extra — correctly absent).

**Fix:** de-listed `JET` from `Project.toml` `[targets].test` (now `["Aqua","Test",
"Random"]`), `[extras]`, and `[compat]` (commented with `# Bennett-37ib` breadcrumbs +
restore recipe). `test/test_hygiene_aqua_jet.jl` already had a resilient `_JET_OK`
try/catch (`@eval using JET` inside `try`) that **self-skips the JET static-analysis
testset LOUDLY** when JET is absent (or `BENNETT_SKIP_JET=1`) — Aqua hygiene is
unaffected and still runs. No `src/` touched. Also removed a stale *untracked*
`test/Manifest.toml` (May-23, missing JET+Aqua) that emitted `Entry in manifest differs`
reconcile warnings every run — Pkg regenerates the test env from root `[extras]`/`[targets]`.

**Verified GREEN:** `Bennett | 689016 passed, 0 failed, 3 broken, Total 689019,
25m53s; Testing Bennett tests passed; PKGTEST_EXIT=0`. The 3 Broken are pre-existing
`@test_broken` Aqua-ambiguity advisory markers (not regressions). Precompile never
touched JET. Restore auto-runs (no flag flip) once JET is re-listed — tracked in
**Bennett-pljv** (P3): only re-list after confirming JET precompiles without hanging
under the test config.

**Env note (doc drift):** this machine runs **Julia 1.12.3** (juliaup), not 1.12.5 as
the bead title / CLAUDE.md state. Worth reconciling the documented Julia version.

## Session log — 2026-06-23 — Bennett-beaw: ConstantPointerNull → zero cell under ptr_cells

**CW-D lever.** Model a `ptr null` (LLVM `ConstantPointerNull`) operand as a
zero 64-bit VM cell under the closed-world `ptr_cells=true` gate. A null pointer
is address 0 and a pointer is one Int64 VM cell (ADR 0018 §A), so `ptr null` →
`iconst(0)` (`ConstOperand(0)`) at width 64. On the circuit path
(`ptr_cells=false`) it stays FAIL-LOUD — the Bennett-bjdg / U80 behaviour,
byte-identical. The circuit/:heap models have no canonical zero-cell pointer
semantics, so the null→0 modeling is strictly gated.

This is the fdict-root successor wall past iwo9 (type-tag round-trip) and r92o
(gc_alloc_obj). Pre-fix, the real `fdict_d1b(a,b) = (d=Dict{Int8,Int8}();
d[a]=b; d[a])` root walled (optimize=false, ptr_cells=true) verbatim at:

> ir_extract.jl: ConstantPointerNull operand: ptr null — null-pointer
> dereference. Bennett.jl does not currently lower null-pointer operands.
> (Bennett-bjdg / U80)

from the `store ptr null, ptr %obj` field-inits in the inlined
setindex!/getindex body.

### _operand-threading approach (minimal, mechanical)

`_operand(val::LLVM.Value, names)` is a HOT path with ~80 call sites across
`src/extract/*.jl` — threading a positional/required `ptr_cells` everywhere
would be a huge, risky diff. Instead: added a **defaulted kwarg**
`ptr_cells::Bool=false` to the `LLVM.Value` method ONLY. Every existing call
site compiles against the same method and is byte-identical (default false →
the U80 fail-loud for null still fires). Only the TWO ptr_cells-gated call
sites that can actually receive a `ptr null` pass `ptr_cells=true`:

1. `src/extract/instructions.jl` — the `ret` arm (the `ptr_cells && ... isa
   PointerType` branch): `IRRet(_operand(ops[1], names; ptr_cells=true), 64)`
   — handles `ret ptr null`.
2. `src/extract/instructions.jl` — the `store` arm (the `ptr_cells && vt isa
   PointerType` branch): `IRStore(ssa(...), _operand(val, names;
   ptr_cells=true), 64)` — handles `store ptr null, ptr %obj`.

The `_VectorLaneValue` overload of `_operand` (vectors.jl:69) is NOT touched —
it's a separate method on a non-`LLVM.Value` type and the vector lane path never
carries a `ptr null`. No conflict.

The model itself lives in `src/extract/helpers.jl` `_operand`, in the precise
`LLVMConstantPointerNullValueKind` arm (the value-kind C-API check, NOT a
Julia-level type — LLVM.jl doesn't expose one; Rule 5). Added `ptr_cells &&
return iconst(0)` BEFORE the U80 `error(...)`. Critically left
ConstantFP / PoisonValue / UndefValue arms UNTOUCHED — they are NOT null
pointers and have no canonical zero-cell meaning, so they stay fail-loud under
BOTH gates.
