# Worklog chunk 094 — bennettvm-416r.16 caller-side consumed-sret reconciliation

## Session log — 2026-07-12 — bennettvm-416r.13: clear the `jl_global#NNN` runtime wall (front-end half)

**Bead:** bennettvm-416r.13 (+ tail of 416r.4). Implementer in a 3+1 (base
Design B; adopted A's D2 fail-loud + A's D5 poison-consideration). Cross-repo;
BVM half in that repo's WORKLOG.

**The wall.** `run!` on the lowered 4-function fdict set threw `KeyError:
Symbol("jl_global#NNN")` in `Define.forward` at Dict construction. Root cause:
the front-end DROPPED the empty-`GenericMemory` singleton load `%x = load ptr,
ptr @"jl_global#NNN"` (matched no arm) and left a dangling SSA operand.

**Front-end change (this repo).** ~3 files, ~70 LOC:
- `src/extract/constexpr.jl`: new `_is_singleton_data_global_name(s) =
  occursin(r"^jl_global#\d+$", s)` beside `_is_type_tag_global_name`.
- `src/extract/module_walk.jl`: `_extract_const_globals(mod, ptr_cells=false)`
  — seed a zeroed **16-cell / ew-8** header for each `jl_global#N`.
- `src/extract/instructions.jl`: load handler — singleton arm ALIASES the
  load-result SSA name to the canonical global-var name (`names[inst.ref] =
  Symbol(pname)`; drops the load), so all N drifting load-result names of one
  singleton collapse to the single `.globals` key (the "loaded twice" wrinkle,
  Design B D3). Plus the A-D2 tightening: an UNRECOGNIZED `ptr_cells` pointer-
  load through a GlobalVariable now `_ir_error`s (was a silent `return nothing`
  → dangling).

**GROUND-TRUTH SURPRISE #1 (where the singleton is recognised).** The census /
both designs said to add the singleton arm in the `_extract_const_globals`
`else` fall-through (after the readable-data arms). WRONG: `LLVM.initializer(g)`
**THROWS** `Unknown value kind LLVMGlobalAliasValueKind` for a `jl_global#N`
(its aliasee is an unrepresentable `inttoptr`), so the benign catch sets `init =
nothing` and the code `continue`s at line 953 — the `else` is NEVER reached. The
throw IS the opaque-initializer signature (a readable-data global never throws
there). Moved the real arm to the `init === nothing` branch; kept a
belt-and-suspenders arm in `else` for a hypothetical future representable
aliasee. Adapted mechanically + documented (contradiction clause — a mechanical
detail).

**GROUND-TRUTH SURPRISE #2 (cell addressing — settled empirically).** Census Q1
said the construction GEP lowers to `Define(.., :add, 1)` (8-byte cells); Design
B's probe said `:add, 8` (byte cells). **B is right:** the GEP is `getelementptr
i8, …, 8` → `elem_width=8 bits` (1-byte cells) → `offset_bytes 8 ÷ ew_bytes 1 =
8`. Data-ptr lands at **cell base+8**, length at base+0 → 16-cell header is
correct.

**POISON decision (fell back to 0, documented).** A's D5 poison (seed data-ptr@8
with a `>= GLOBAL_BASE` sentinel) is architecturally incompatible with B's
BINDING channel choice (reuse `.globals`, no new field): the front-end must not
bake a VM address into IR (layer split), and the VM cannot distinguish a
singleton header from a real const array in the shared `(Vector{UInt64},ew)`
channel. Ground truth also confirms the data-ptr@8 read is inert (feeds a
compile-time len-0 memset; the fdict run never dereferences it). So: ship zeros;
the VM read-window trap (D5) covers the out-of-header miscompile class instead.

**Tests.** `test/test_416r13_jlglobal_singleton.jl` (new, 16 assertions): the
fdict SET root seeds `jl_global#…` 16-cell/ew-8 headers (count/shape, no `#NNN`
pinned); zero dangling `jl_global…` operands across the set (aliasing works); an

the GC preamble, so the test uses `extract_parsed_ir_set_from_julia`.
Registered in runtests after `test_416r16_consumed_sret_reconcile`.

**Regressions (--check-bounds=yes):** test_8kno (the `_extract_const_globals`
dedicated test) 8/8, qal5 10/10, haiy 39/39, d1b 33/34 (1 pre-existing broken),

**NEXT WALL (successor bead).** With the jl_global wall cleared, the fdict(3,7)
run advances past construction, past the GC-preamble TLS read, INTO
setindex!/rehash!/ht_keyindex2, and back to the root — where the final `d[a]`

## Session log — 2026-07-11 — bennettvm-416r.16: the LAST static wall of the CW-D fdict chain

**Bead:** bennettvm-416r.16 (implementer role in a 3+1; reviewer chose Proposer A's
front-end reconciliation). **Files:** `src/extract/sret.jl` (recognizer + post-pass),
`src/extract/module_walk.jl` (integration), `test/test_416r16_consumed_sret_reconcile.jl`
(new), `test/runtests.jl` (register), plus updates to `test_416r17` (c) and
`test_xrd6` (a). BVM side in that repo's worklog.

### What it does
`setindex!`'s `ht_keyindex2_shorthash!(sret_box, h, key)` call returns `{i64,i8}`
by sret into a LOCAL `alloca [2 x i64]` box whose fields it reads back (NOT
forwards to a parent sret). Pre-416r.16 (Bennett-xrd6) that extracted as a
box-cell-arg `IRCall(dest=__v1, callee, [box, h, key], [64,64,8], rw=64)` +
`IRLoad`s off the box — the sret_box MEMORY ABI. BennettVM guard-5 walled: the
callee returns a 72-bit aggregate but `ret_width=64 ≠ 72`. This was the last
static wall before `lower_vm(fdict set)` completes.

The fix (ptr_cells-gated, front-end): a caller-side consumed-sret recognizer
`_collect_consumed_sret` (sibling of `_collect_sret_writes` /
`_try_handle_sret_memcpy_reject!`), integrated in `module_walk` where those run.
It suppresses the box `IRAlloca` + its const-offset GEPs, rewrites the call to
the VALUE ABI (`IRCall(__v1, callee, [h,key], [64,8], 72)` via
`_cell_call_args(...; skip_sret=true)`), and rewrites the box field reads to
heterogeneous `IRExtractValue` (`elem_width=0, n_elems=2, field_widths=[64,8]`,
dense k order). Result: consumed call value-ABI [64,8]/72, 5 field reads →
IRExtractValue with indices {0,0,0,0,1}. `lower_vm(set)` COMPLETES → VMProgram.
**The CW-D static-wall chain is DONE.**

### A-vs-B layer decision (why front-end, not BVM reconstruction)
The field byte offsets `{0,8}` are `{i64,i8}`'s x86-64 SysV layout, read from the
call-site `sret(<ty>)` pointee via `LLVMOffsetOfElement` (mirroring
`_sret_struct_fields`). A BVM-side reconstruction would have to re-derive offsets
from widths, but hetero structs have PADDING (offset ≠ Σwidths), so that is
silent-miscompile-prone. The byte offsets are front-end ground truth — reconcile
where the LLVM datalayout is live.

### THE SURPRISE: field 1 is read by a memcpy, not a load (design census was wrong)
The design/task census said the box is consumed by "5 loads, nothing else." REALITY
(dumped `code_llvm` at optimize=false): field 0 (i64) is read 4× via plain
`load i64`, but field 1 (i8) is read by a **1-byte `llvm.memcpy` (SOURCE)** copying
the shorthash byte into the Dict's `slots`/data array — NOT a `load`:

```
%sret_box = alloca [2 x i64]
call void @ht_keyindex2(sret({i64,i8}) %sret_box, ...)
%"sret_box[2]_ptr" = getelementptr i8, ptr %sret_box, i32 8
%unbox   = load i64, ptr %sret_box          ; field 0 (×4)
call void @llvm.memcpy(ptr %memoryref_data, ptr %"sret_box[2]_ptr", i64 1)  ; field 1 read!
```

The design's "5 loads" was describing the EXTRACTED ParsedIR, not the raw LLVM:
the extractor's memcpy handler lowers a field-width memcpy to `IRLoad(field_ptr)
+ IRStore`, so at the ParsedIR level field 1 IS an `IRLoad(sret_box[2]_ptr, 8)`
(dest `__v74`). My first cut keyed the load→IRExtractValue rewrite off the LLVM
`load` ref and fail-loud'd on the memcpy use ("box GEP used by a non-load
instruction"). **Adaptation (mechanical, per the task's contradiction clause):**
the rewrite is now a ParsedIR POST-PASS `_apply_consumed_sret_loads!` keyed by
ptr SSA NAME (box name → field 0; each GEP name → field k). It rewrites EVERY
`IRLoad(ptr∈map)` — plain loads AND the memcpy-synthesised one — to
`IRExtractValue`, then asserts no suppressed name still dangles. The LLVM-level
box-use validation now ALLOWS a memcpy whose SOURCE is the box/GEP (a field read)
and rejects a memcpy whose DEST is the box (a store into it). This is why the
recognizer is split: LLVM pre-pass (recognise call, suppress box+GEPs, validate
uses, build value-ABI IRCall + name→field map) + ParsedIR post-pass (rewrite
loads by name). A memcpy reader has no LLVM `load` ref to key on — hence by-name.

### Mutual exclusivity of the two sret recognizers
Forwarding (`_try_handle_sret_memcpy_reject!`, box memcpy'd to PARENT sret) runs
only when the enclosing function has an sret param; it populates
`call_return_suppressed`. `_collect_consumed_sret` SKIPS any box in that set and
asserts `isempty(intersect(suppressed, forwarding_suppressed))`. `setindex!` has
no sret param → forwarding set empty → every sret-out box is consumed.
`ht_keyindex2_shorthash!` DOES have sret and its recursive self-call is FORWARDED
(the 416r.17 path, [64,8]/72) — my recognizer skips that box (forwarding claimed
it), so 416r.17's recursive-call pin is untouched. A box is EITHER forwarded OR
consumed, never both.

### One-site census (fdict set)
EXACTLY ONE consumed-sret call in the whole set: setindex!'s `ht_keyindex2`
(box=local alloca, consumed). The recursive rw=72 call in ht_keyindex2's own body
is value-ABI FORWARDING (untouched). Both bounds modes (default AND
`--check-bounds=yes`) extract setindex! with the same box shape (the iwo9 ptrtoint
wall that xrd6 documented was cleared by a later bead — setindex! now extracts
under check-bounds too).

### param-width 512 inertness
`h::Dict`'s LLVM param carries width 512 (`ptr addrspace(10)` deref); it is inert
— `FunctionEntry`/args discard param widths, and `_cell_call_args` carries the
ptr as a 64-bit cell. NOT touched.

### The runtime successor (out of scope)
`lower_vm(set)` COMPLETES → VMProgram (4 functions; `ht_keyindex2_shorthash!`
returns arity 2, ret_elem_widths [64,8]). The first RUNTIME wall is jl_global
const-global materialization (`KeyError` in Define.forward), successor beads
bennettvm-416r.13 / 416r.4 — NOT this bead.
