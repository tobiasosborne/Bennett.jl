### What shipped

An `julia.gc_alloc_obj` ARENA root is now admitted on **EITHER SIDE** of a
const-size, cell-aligned `llvm.memcpy`, under `ptr_cells`, in
`_handle_memcpy_arm` (`src/extract/instructions.jl`). Route R1: the per-cell
`IRPtrOffset + IRPtrOffset + IRLoad + IRStore` decomposition, with the
**Bennett-4y0d address/value split applied PER SIDE**:

| side | root | scale | `IRPtrOffset` stamp | cell of element k |
|---|---|---|---|---|
| arena | `julia.gc_alloc_obj` | 1 | 8 | `base + 8k` |
| alloca | `alloca i64` / `[N x i64]` | 8 | 64 | `base + k` |

with the `IRLoad`/`IRStore` VALUE width 64 on **both** sides. The cell-map
argument: each side is an INDEPENDENT address computation off its own root; the
quantity they share is the 64-bit VALUE, which occupies exactly ONE cell in BOTH
tiers (byte tier at the value's base byte address, `+1…+7` never named — the
416r.13 / 9n3y / vbv9 convention; word tier at cell k). So `K = N/8` and element
k is the single-cell move `src_cell → dst_cell` under each root's own map.

Both directions are gated: arena→alloca (the corpus main, ×3 sites) and
alloca→arena (corpus site #6 at `%L18`, which the scout recommended scoping in
rather than deferring — the predicate work is shared and an asymmetric arm
re-walls on the same function for the transposed reason).

### The three new/changed predicates

1. **Predicate 6 (both halves), gated.** `arena_dst` / `arena_src` are consulted
   only under `ptr_cells`, so the two reject messages are **character-identical**
   on the circuit path. `test_37mt` (86/86) and `test_lqif` (12/12) pin that.
2. **Predicate 6c — NEW, and genuinely new (not a vbv9 copy).** An arena
   operand's byte offset from its root must be a compile-time CONSTANT and a
   multiple of 8. New helper `_gc_alloc_root_offset` (mirrors
   `_global_root_and_offset`'s index arithmetic, bottoms out at the gc_alloc
   call, reuses `_gc_alloc_root_ref` as its bottom-out predicate so the two
   walkers cannot disagree).
   **Why (SC) cannot supply this** — the non-obvious bit worth writing down:
   `gep i8 %obj, 4` off a byte-tier root is *perfectly scale-coherent* (stamp 8,
   scale 1, cell +4). `_check_scale_coherence!` is therefore silent, yet the
   byte tier names a 64-bit value by its BASE byte address only, so an 8-byte
   chunk starting at byte 4 straddles two named cells and no `IRLoad`/`IRStore`
   pair expresses it. Coherence and expressibility are different properties.
   **Residual filed:** vbv9's arena-DST branch on the global-src path has the
   same unchecked corner (its G7 checks the *global's* offset only) — noted in
   the arm comment, tracked on Bennett-8bys.
3. **Predicate 7 GENERALISED** from "same alloca ref" to "same ROOT ref,
   whichever kind". This is **load-bearing and it REPLACES a check rather than
   adding one** — route R1 never emits an `IntrinsicMemcpy`, so
   `forward(::IntrinsicMemcpy)`'s runtime overlap check
   (`intrinsics_bulk.jl:117-121`) is simply not in the path, and R1's ascending
   per-element load-then-store genuinely miscopies an overlapping range.
   The alloca↔alloca message is kept byte-identical (`test_37mt:101` pins
   "same alloca"); an arena root on either side gets its own text.

**The vau9 asymmetry, so nobody reads it as an inconsistency:** memmove is
*allowed* to overlap and routes to `IRCall(:memmove)` because BVM's
`_copy_range!` snapshots the whole src range before writing — overlap-safe by
construction. memmove DELEGATES overlap safety to the VM; sy29 must PROVE
disjointness at extraction. For the corpus that proof is **structural**: the src
root is a `gc_alloc_obj` served from the ARENA region (`arena_top`) and the dst
root an `alloca` served from the STACK region (`stack_top`), so no dynamic
execution can make them alias.

**Reversibility for the arena-DST direction** cites **u2kk**, not vbv9. The
mirror write is a DESTRUCTIVE overwrite of a live cell; vbv9's STEP-0c freshness
argument does not cover it. It is reversible because BVM logs every cell store
on its Bennett-1973 history tape. Freshness is a circuit-model artifact, which is
exactly why the whole branch is `ptr_cells`-gated.

### The K=1 trap — the reason gate (b) exists

`_check_scale_coherence!`'s vacuity exemption (`instructions.jl:593`) skips a
node whose emitted and intended cells COINCIDE — canonically offset 0. **At
K = 1 the only offset IS 0**, so an arena-side node wrongly stamped 64 passes
(SC) *silently*. That is precisely how the pre-4y0d vbv9 defect stayed green
behind `test_vbv9_arena_memcpy.jl`'s K=1 pins — and **the whole push! corpus is
K = 1**. A K=1-only RED test would have proven nothing. `test_sy29` gate (b) is
a K=2 arena-src fixture asserting `(8, 8)` at `k = 1`, and the BVM E2E is K=2 in
both directions for the same reason.

**D2 (MAJOR, code fix) — the disjointness argument was a FALSE THEOREM.** The
shipped comment claimed "two distinct static allocation sites yield disjoint
ranges, because both allocators are monotone bumps". Executed counterexample
(reviewer probe `p2_overlap_vm`): BennettVM's arena is a monotone bump, so a
16-byte `gc_alloc_obj` `%a` is immediately followed by `%b` and **`%a + 24` IS
`%b + 8`**. A memcpy with dst rooted at `%a` and src at `%b` has DISTINCT ROOTS
and GENUINELY OVERLAPPING RANGES; route R1's ascending load-then-store miscopied
it — **`s = 222` against an oracle of `333`**. Second symptom from the same hole:
an arena src range past its own reservation silently **read the next object**
(`leak = 999`). Monotone bumps make distinct *allocations* disjoint; they say
nothing about distinct *roots* once a GEP walks out of its own object.

Fix: **Predicate 6d, the IN-OBJECT RANGE guard** — `0 <= off` and
`off + N <= capacity` on BOTH operands. Both halves already existed:
`_root_scale` returns capacity (`gc_alloc → (1, nbytes)`, `alloca → (ew÷8, n)`,
`malloc → (8, nb÷8)`), and a new root-kind-agnostic `_root_byte_offset` supplies
the offset from that same root (`_gc_alloc_root_offset` now delegates to it, so
there is ONE recursion, not two). The predicate ships one arm over already —
`_handle_memcpy_global_src`'s G8 bounds-checks the global side. **This also
closes a PRE-EXISTING alloca↔alloca hole at HEAD** (reviewer probes A1/A2): the
alloca path never had a bounds check either, and the generalised predicate now
owns both, on the circuit path as well as under `ptr_cells`. Skipped, narrowly,
only when capacity is unprovable (`_root_scale === nothing`: param/global/phi/
load with no reservation in this function; or a runtime-count alloca). An
unresolvable OFFSET against a PROVABLE capacity fails loud — we know there is a
bound and cannot show the access respects it. A boundary control pins that an
EXACTLY-fitting range (`off + N == cap`) is still admitted, since the corpus
itself is flush.

**The corpus is flush on BOTH sides, and that turns out to be the mutation test
for 6d.** src: `gep i8 %"new::Array", 16` off `gc_alloc_obj(_, 24, _)` →
`16 + 8 == 24`. dst: `alloca i64` → `0 + 8 == 8`. So `<=` vs `<` is exactly the
difference between admitting and rejecting the corpus, which makes the predicate
**mutation-verifiable without a synthetic fixture**: flipping `<=` to `<` was
measured to reject the push! corpus at 6d. That is the evidence that 6d
genuinely EVALUATES on the corpus rather than being silently skipped by its own
`_root_scale === nothing` / `cap < 0` guards — a real risk for a predicate whose
skip conditions are broad, and the thing a green corpus run alone would NOT have
shown.

### Emission byte-identity for every pre-sy29 client — argued from definitions

`ptr_ew_src`/`ptr_ew_dst` now come from `_root_scale`, ungated (matching vbv9).
That is byte-identical everywhere it was reachable before, and the argument is
structural rather than empirical: `_root_scale` bottoms out at
`_alloca_reservation`, the SAME source of truth the alloca arm reserves from, so
for an integer-typed alloca `8*rs[1] == _alloca_elem_width_bits(root) == dst_ew`.
The three places they *could* differ are all unreachable — a pointer-typed
alloca gives `_alloca_elem_width_bits == 0` and dies at Predicate 8; a
nested-array/non-integer alloca makes `_root_scale` return `nothing` (fallback to
HEAD's `dst_ew`); a sub-byte width (`alloca i1`) fails `_root_scale`'s
`ew % 8 == 0` guard and also falls back.

### Wall 10 landed exactly where the scout said

Verbatim, at `%top`, five instructions downstream of the admitted memcpy:

```
ir_extract.jl: ptrtoint in @julia_f_32102:%top:
  %12 = ptrtoint ptr %memory_data3 to i64
— … predicate `_verify_memdata_bounds_cluster` … (Bennett-583s / CW-D) …
AND its result is not CONFINED to a dead-throw bounds check either —
predicate `_foz5_confined_dead_bounds` (Bennett-foz5 / ADR 0017 §4a) …
```

**Why foz5 §4a clause (iii) fails, precisely** (`instructions.jl:1707-1716`,
(C2)): for each use of the `sub`, the user's opcode must be `LLVMICmp`. Here the
`sub`'s **only** use is `udiv exact` ⇒ the loop returns `false` on the first
iteration. Note what does NOT fail: (C0) passes (both `ptrtoint` sources are
certified `:load`s) and (C1) passes (single 64-bit `sub` of two `ptrtoint`s).
**The cluster is ONE OPCODE from foz5's contract, and that opcode is the whole
difficulty** — the difference does not merely *steer* a halting branch, it
becomes the element index and **escapes into two closure-env stores**
(`env+8`, `env+16`) that `_growend!` reads. Wall 10 needs a THIRD admission
contract; **not designed here**. Data offered to whoever scouts it: under the
Julia byte tier a VM cell index IS a byte address, so a cell difference equals
the native byte difference and the `÷8` is faithful — but that is exactly the
premise foz5 §4a *declined to prove*.
