### The three findings that force the upgrade

**1. The bead's named mechanism clears no wall.** Emitting
`IRPtrOffset(_,_,8k,8)` per field widens **(P4b)** only; the very next
predicate, **(P5)**, then fires on the real corpus use-shape. Executed proof
(`b06_p5.jl`): the same use pattern on a `malloc` target — which (P4b) *does*
certify — rejects with *"addressed at BOTH the WORD granularity … via the
single-index BYTE-granular getelementptr"*. An implementer who reads only the
bead ships a no-op.

**2. The CW-D4 split is ALREADY live in the root, independent of the store.**
Measured stamps (`b04_stamps.jl`) on one and the same `%"new::Array"`:

```
gep i8        %obj, 8       -> IRPtrOffset(_, obj,  8,  8)  -> cell obj+8
gep {ptr,ptr} %obj, 0, 1    -> IRPtrOffset(_, obj,  8, 64)  -> cell obj+1
```

Byte offset 8 maps to **two different cells**. There are **6** such two-index
struct-GEP loads (2 each in `%top`, `L21`, `L43`) against **5** byte GEPs. So
byte-stamping the store alone converts "store word, read byte" into "store byte,
read word" — still broken, differently. The fix requires re-stamping the **D4
two-index struct-GEP arm** (`instructions.jl:4977`), i.e. **Bennett-zdd6** (the
real filing of the dangling "jb6w"), whose discriminator is shared with the C
tier and with the 416r.13 singleton headers.

**3. The Julia tier is byte-addressed EVERYWHERE, including stack frames.**
`b09_alloca.jl`, executed on the root's own shapes:

```
alloca [9 x i64]           -> IRAlloca(:env, 64, 9)          # BVM reserves 9 cells
gep i8 %env, 56            -> IRPtrOffset(:g56, env, 56, 8)  # addresses cell env+56
alloca ptr, i32 3          -> IRAlloca(:roots, 64, 3)
gep i8 %roots, 16          -> IRPtrOffset(:r16, roots, 16, 8)
```

The closure-env write lands **48 cells past its own reservation**. Store/load
through the same GEP are self-consistent, so read-back looks fine — the failure
mode is **silent adjacent-allocation clobber**, which `bennettvm-pdqx`
explicitly does not catch (p06b's own D1 disclosure, verbatim). **No patch to
the p06b store arm can reach this.** It is live in the corpus root; walls 9/10
merely sit in front of it.

### The 416r.13 question, answered

**The corpus store is NOT the header write.** Value type is literal
`{ptr,ptr}` (GenericMemoryRef body), not `{i64,ptr}`; there is no live
`store {i64,ptr}` anywhere. **(P1) stays intact and is untouched by this arc** —
the widening is (P4b)-granularity only. But the 416r.13 *interaction* is real
and lives in the D4 arm: the header byte-stamp is **type-based**
(`_is_genericmemory_header_struct`), and the 416r.13 singletons are **globals**
with no `gc_alloc_obj` root (10 header GEPs measured in the root, including
`gep {i64,ptr}, ptr @"jl_global#93", 0, 1`). ⇒ **any provenance-based
discriminator must be a UNION with the type-based one, never a replacement**, or
the shipped `length@byte-cell 0 / data@byte-cell 8` layout silently demotes to
word granularity.

**Nomenclature:** `bennettvm-9n3y` is a **dangling ID in neither tracker**
(recorded in `bennettvm-rxgy` NOTES). Live filings: **Bennett-zdd6** (mis-stamp
discriminator) and **bennettvm-rxgy** (byte-exact memmove). `test_p06b` (N3)
currently pins the literal string `9n3y` — do not propagate it.
